# Выполнение задания агентом: сессии, промпты, повторы

Схема для минимального случая: есть только ИИ-агент, задание заказчика и этот репозиторий; трекера и команды нет. Это урезанное применение методологии (README, раздел 3): человек совмещает роли владельца и оркестратора, агент в разных сессиях играет исполнителя и проверяющего. Работа внутри каждой сессии идёт по [task-algorithm.md](task-algorithm.md), правила повторов взяты из README, раздел 10, требования к текстам наружу — из раздела 12.

Планирование и реализация разделены точкой утверждения плана. Между ними может пройти любое время, и их могут выполнять разные агенты: всё состояние лежит в файлах, промпты не опираются на прошлые разговоры.

## Схема

```
Подготовка (вы)
   ↓
С1 Разбор ─────────────────→ spec.md (черновик)
   ↓
С2 Проверка разбора ───────→ spec-review-N.md
   ├─ есть существенные ──→ С1 правка ──→ С2 заново
   ↓ два захода подряд без существенных
Вы: вопросы заказчику, ответы, подтверждение сценариев
   ├─ ответ меняет цель, границы, сценарии ──→ С1 правка ──→ С2
   ↓
spec.md: «утверждено»                              ══ граница 1 ══
   ↓
С3 План ───────────────────→ plan.md (черновик, базовая ревизия)
   ↓
С4 Проверка плана ─────────→ plan-review-N.md
   ├─ есть существенные ──→ С3 правка ──→ С4 заново
   ├─ план требует менять требования ──→ С1 правка ──→ С2 ──→ граница 1 ──→ С3 правка
   ↓ два захода подряд без существенных
Вы: решения из списка «требует утверждения»
   ↓
plan.md: «утверждено»                              ══ граница 2 ══
   ↓            любое время, любой агент
С5 Реализация ─────────────→ код + result.md
   ├─ код ушёл от базовой ревизии ──→ С3 правка ──→ С4 ──→ граница 2 ──→ С5
   ├─ нужен шаг или файл вне плана ─→ С3 правка ──→ С4 ──→ граница 2 ──→ С5
   ├─ вопрос ───────────────────────→ вы отвечаете ──→ С5 продолжает
   ↓
С6 Проверка реализации ────→ review-N.md
   ├─ дефект реализации ──→ С5 правка ──→ С6 заново
   ├─ ошибка плана ───────→ С3 правка ──→ С4 ──→ граница 2 ──→ С5 правка ──→ С6
   ├─ ошибка требований ──→ С1 правка ──→ С2 ──→ граница 1 ──→ С3 правка ──→ …
   ↓ два захода подряд без существенных
С7 Сдача ──────────────────→ delivery/
   ↓
С8 Проверка сдачи ─────────→ delivery-review-N.md
   ├─ есть существенные ──→ С7 правка ──→ С8 заново
   ↓ два захода подряд без существенных
Вы: коммит и пуш, отправка заказчику
   ↓
Обратная связь ──→ С9 Разбор обратной связи ──→ feedback-N.md
   ├─ требования ──→ С1 правка ──→ С2 ──→ граница 1 ──→ С3 правка ──→ … ──→ С8
   ├─ план ────────→ С3 правка ──→ С4 ──→ граница 2 ──→ С5 правка ──→ … ──→ С8
   └─ реализация ──→ С5 правка ──→ С6 ──→ С7 ──→ С8
```

Папка задачи лежит рядом с репозиторием и в репозиторий не коммитится:

```text
task-algorithm.md
task/                  всё от заказчика как есть
task/feedback-N/       обратная связь после сдачи
spec.md                спецификация; статус в первой строке
spec-review-N.md
plan.md                план; статус и базовая ревизия в первых строках
plan-review-N.md
result.md              отчёт реализации
review-N.md
delivery/              тексты наружу
delivery-review-N.md
feedback-N.md          разбор обратной связи
log.md                 ваш журнал: строка на каждый заход
```

## Правила

- **Всё состояние в файлах.** Любую сессию можно начать заново любым агентом.
- **Статус в первой строке spec.md и plan.md:** «черновик» или «утверждено: дата, кто». Ставите его только вы. Любая правка после утверждения возвращает статус «черновик», и документ заново проходит проверку и утверждение.
- **Реализация начинается только с утверждённых spec.md и plan.md.** Если план реализуется не сразу, он сначала сверяется с кодом по базовой ревизии.
- **Проверка всегда в новой сессии**, не в той, что писала. Правку можно делать в любой сессии.
- **Существенная находка** меняет требования, границы, сценарий, план, доказательство, число или то, что уйдёт заказчику. Остальные находки поверхностные и повтора не требуют.
- **Остановка** наступает после двух заходов проверки подряд без существенных находок.
- **Чистый заход засчитывается только с тремя пробами**, показывающими, где и как искали.
- **Потолок четыре захода на этап.** Если существенные находки остаются, вы решаете: урезать объём, спросить заказчика или остановиться.
- **N в промптах** это номер захода: 1, 2, 3. Вместо `<репозиторий>` подставьте путь к коду.

## Промпты

**С1 Разбор**

```text
Прочитай task-algorithm.md целиком. Выполни шаги 1–7 по материалам в папке task
и по коду в <репозиторий>. Результат запиши в spec.md, первая строка «Статус: черновик»:
1. Опись источников: каждый файл, картинка, ссылка, страница, таймкод видео;
   статус: прочитан / прочитан частично (что не получено) / недоступен; итого число.
2. Таблица покрытия: каждое утверждение, пометка, требование из материалов →
   REQ или AC с номером, либо «не требование: причина». Ни один фрагмент не пропускать.
3. Спецификация шага 3; FACT / INFERENCE / UNKNOWN, у каждого источник.
4. Сценарии приёмки AC в форме «когда … тогда», у каждого вид доказательства.
5. Пакет вопросов шага 7: вопрос, почему важен, варианты, умолчание,
   что делается без ответа.
Код не пиши, план не составляй, ничего не коммить. Закончив, остановись.
```

**С1 правка**

```text
Прочитай task-algorithm.md, spec.md и <файл с находками или ответами>:
spec-review-N.md, plan-review-N.md, review-N.md, feedback-N.md или раздел «Ответы» в spec.md.
Исправь spec.md по каждой существенной находке и каждому ответу. Первая строка
«Статус: черновик». Допиши «Изменения захода N»: что исправлено, что отклонено и почему.
Код и план не трогай, ничего не коммить.
```

**С2 Проверка разбора**

```text
Ты не писал spec.md. Прочитай task-algorithm.md, все материалы в папке task,
spec.md и все предыдущие spec-review-*.md.
Найди, что spec.md пропустила или исказила: источник не в описи; фрагмент без строки
в таблице покрытия; требование без источника; неверно понятый скриншот или видео;
вопрос, закрытый догадкой; сценарий, который нельзя проверить; граница «не делаем»,
противоречащая материалам.
Если это не первый заход: закрыты ли прошлые находки и не сломали ли правки соседнее.
Каждая находка: что не так; цитата из материала; место в spec.md;
критичность: существенная или поверхностная.
Если существенных нет, покажи три разных способа, которыми искал.
spec.md не правь. Запиши результат в spec-review-N.md.
```

**Вы после С2.** Прочитайте в spec.md цель, список «не делаем» и сценарии. На вопросы, ответ на которые знаете, ответьте сами. Остальные вопросы и сценарии отправьте заказчику одним письмом. Ответы впишите в раздел «Ответы» в spec.md с пометкой, кто ответил. Если ответ что-то меняет, запустите С1 правку и С2. Когда всё сошлось, поставьте в первой строке «Статус: утверждено, дата, кто».

**С3 План**

```text
Прочитай task-algorithm.md и spec.md. Если статус spec.md не «утверждено»,
остановись и сообщи. Выполни шаги 8–11 по коду в <репозиторий> и запиши plan.md:
первая строка «Статус: черновик»; вторая «База: ревизия <хеш коммита>, дата».
1. Карта шага 8: каждый REQ → файл и функция → какое изменение.
2. Решение шага 9: изменения контрактов, схемы данных, зависимостей, конфигурации;
   граничные случаи; риски. Решения из перечня шага 9 вынеси отдельным списком
   «требует утверждения».
3. DoD шага 10: каждая строка с видом доказательства.
4. План шага 11: шаги по порядку зависимостей, у каждого проверяемый результат;
   что подготовить в окружении.
Если для плана нужно изменить требования, не меняй spec.md: запиши это последним
абзацем и остановись. Код не пиши, ничего не коммить.
```

**С3 правка**

```text
Прочитай task-algorithm.md, spec.md, plan.md и <файл с находками>:
plan-review-N.md, review-N.md, feedback-N.md или вопрос в конце result.md.
Исправь plan.md по каждой существенной находке. Если код ушёл от базовой ревизии,
обнови карту по текущему коду и вторую строку «База». Первая строка
«Статус: черновик». Допиши «Изменения захода N»: что исправлено, что отклонено
и почему. Код не пиши, spec.md не трогай.
```

**С4 Проверка плана**

```text
Ты не писал plan.md. Прочитай task-algorithm.md, spec.md, plan.md, код в <репозиторий>
на базовой ревизии из plan.md и все предыдущие plan-review-*.md.
1. Каждый REQ и AC из spec.md есть в карте и в DoD; в плане нет ничего сверх spec.md.
2. Указанные файлы и функции существуют и делают то, что план предполагает;
   проверь по коду, кто их вызывает.
3. Не пропущены соседние места: все пути с той же логикой, документация,
   конфигурация, миграции, тесты.
4. Каждая строка DoD проверяема указанным доказательством.
5. Решения, требующие утверждения, вынесены в список, а не спрятаны в плане.
6. Если не первый заход: закрыты ли прошлые находки.
Каждая находка: что не так; чем доказано (файл, строка, вывод команды); критичность;
уровень: ошибка плана или ошибка требований.
Если существенных нет, покажи три разных пробы, где искал.
plan.md не правь. Запиши результат в plan-review-N.md.
```

**Вы после С4.** Прочитайте список «требует утверждения» и шаги плана. Решения, которые не можете принять сами, отправьте заказчику. Когда всё сошлось, поставьте в первой строке plan.md «Статус: утверждено, дата, кто». С этого момента реализацию можно начинать в любое время и любым агентом.

**С5 Реализация**

```text
Прочитай task-algorithm.md, spec.md и plan.md. Если статус любого из них
не «утверждено», остановись и сообщи.
Сначала сверь текущую ревизию <репозиторий> с базой в plan.md. Если файлы из плана
изменились после базы, запиши, какие и как, последним абзацем result.md и остановись.
Затем выполни шаги 12–17 строго по plan.md. Детали внутри шага плана меняй сам
и записывай. Если нужен шаг или файл вне плана, меняются контракты или DoD:
запиши последним абзацем result.md и остановись.
Вопрос или противоречие источников: тоже последним абзацем и остановись.
Не коммить и не пушь: срезы оставляй в рабочем дереве.
Доказательства по шагу 10; для исправления дефекта нужен красный прогон до правки.
Отчёт по шаблону RESULT шага 17 и таблицу трассировки шага 16 запиши в result.md.
```

**С5 продолжение после вопроса**

```text
Ответ на вопрос в конце result.md: <ответ>. Источник: <кто ответил или какой документ>.
Запиши как FACT с этим источником и продолжай с места остановки.
```

**С5 правка**

```text
Прочитай task-algorithm.md, spec.md, plan.md, result.md и <файл с находками>:
review-N.md или feedback-N.md. Бери только находки уровня «реализация».
По каждой выбери исход по шагу 18: правлю / отвечаю доводом / отвергаю с обоснованием.
Исправь, заново прогони затронутые проверки шага 13, обнови доказательства в result.md
и допиши «Изменения захода N».
Если для исправления нужно менять план или требования, не исправляй: запиши последним
абзацем и остановись. Ничего не коммить.
```

**С6 Проверка реализации**

```text
Ты не писал этот код. Прочитай task-algorithm.md, материалы в папке task, spec.md,
plan.md, result.md, diff рабочего дерева в <репозиторий> и все предыдущие review-*.md.
1. Перепрогони сам каждое доказательство из result.md; выводам отчёта не верь.
2. По каждому AC: выполнен ли он по поведению и по исходным материалам,
   а не только по spec.md.
3. Код соответствует plan.md; каждое отклонение записано в result.md.
4. Негативные сценарии, регрессии, do_not_change; файлы, которые задача должна была
   тронуть, но не тронула: документация, конфигурация, версии.
5. Если не первый заход: закрыты ли прошлые находки и что могли сломать правки.
Каждая находка: что не так; чем доказано (команда и её вывод); как воспроизвести;
критичность; уровень: реализация, план или требования.
Если существенных нет, покажи три разных пробы, где искал.
Код не правь. Запиши результат в review-N.md.
```

**С7 Сдача**

```text
Прочитай spec.md, plan.md, result.md и последний review-*.md. Подготовь в папке delivery:
1. commit.txt: сообщение коммита;
2. customer.md: текст заказчику. Что сделано; как проверить; по каждому сценарию,
   чем он закрыт; что не сделано и почему;
3. mr.md, если результат сдаётся merge request: что и зачем, как проверить,
   влияние на контракты, что осталось за границами.
Только факты из result.md, у которых есть доказательство. Никаких внутренних путей,
номеров находок, упоминаний ИИ и инструментов, секретов и паролей.
Обещать не больше сделанного. Ничего не коммить и не отправлять.
```

**С7 правка**

```text
Прочитай spec.md, result.md, всё в папке delivery и delivery-review-N.md.
Исправь тексты по каждой существенной находке. Новые утверждения бери только
из result.md с доказательством. Ничего не коммить и не отправлять.
```

**С8 Проверка сдачи**

```text
Ты не писал эти тексты. Прочитай spec.md, result.md и всё в папке delivery.
По каждому утверждению: есть ли доказательство в result.md; совпадают ли числа;
не обещано ли больше сделанного; понятно ли человеку, который не видел работу;
нет ли секретов, паролей, внутренних путей, упоминаний ИИ; назван ли каждый сценарий
с тем, чем он закрыт.
Каждая находка с критичностью. Если существенных нет, покажи три пробы.
Тексты не правь. Запиши результат в delivery-review-N.md.
```

**Вы после С8.** Скажите агенту: «закоммить с сообщением из delivery/commit.txt и запушь». Если результат сдаётся merge request, откройте его с описанием из mr.md. Текст customer.md отправляете заказчику вы.

**С9 Разбор обратной связи.** Положите ответ заказчика в task/feedback-N, затем:

```text
Прочитай task-algorithm.md, spec.md, plan.md, result.md и всё в task/feedback-N.
Ничего не правь. По шагу 18 разбери каждое замечание: исход (правлю / отвечаю доводом /
отвергаю с обоснованием) и уровень: требования, план или реализация. Для «отвечаю
доводом» и «отвергаю» приложи доказательство. Запиши в feedback-N.md, в конце маршрут:
с какой сессии начинать. Требования → С1 правка; план → С3 правка; только
реализация → С5 правка.
```

Дальше маршрут идёт по схеме. Если поменялись требования, spec.md и plan.md заново проходят проверку и утверждение, и только потом начинается реализация.
