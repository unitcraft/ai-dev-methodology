# Модель хозяина эпика на Алуле

**Статус:** компактная модель контракта; не исполняемая машина и не реализация host. Синтаксические формы типов, вариантов, сторон и событий следуют Алуле. Основание поведения — WC-2 §«Контракт и границы», «Жизненный цикл и полномочия», «Намерение вопроса и эффектов» и WC-3 S01–S03, S09, S14–S15, S20, S22.

## Область модели

Хозяин хранит один корневой `epic`, его рекурсивных потомков и собственный журнал. Хозяин проверяет и фиксирует typed events; исполнитель ребёнка предлагает результат, но не меняет состояние эпика и не удостоверяет решение владельца. Это модель границы и исходов: она не задаёт полный раннер, внешнюю доставку или backend.

## Типы

```alula
тип Работа { id строка, ревизия число, вид ВидРаботы, состояние Состояние }
тип ВидРаботы перечисление Task | Epic
тип Состояние перечисление
  | Queued
  | Ready
  | Running
  | Paused
  | BlockedDependency
  | DeliveryPending
  | WaitingOwner
  | Completed
  | Failed

тип Артефакт { producer строка, stage строка, version строка, acceptance_ref строка }
тип Pin { consumer строка, producer строка, stage строка, version строка, acceptance_ref строка }
тип Ребро { parent строка, child строка }
тип Зависимость { consumer строка, producer строка, pin Pin }

тип KindСобытия перечисление
  | ChildChanged
  | ArtifactAccepted
  | PinReconciled
  | OwnerIntentRecorded
  | DeliveryConfirmed
  | OwnerDecisionReceived
  | RestartRecovered
тип OwnerDecision перечисление Accept | Return | Reject
тип ИсходДоставки перечисление Confirmed | Unknown
тип Receipt { intent_id строка, исход ИсходДоставки }
тип Событие { id строка, target_id строка, expected_revision число, kind KindСобытия, payload_ref строка, actor строка, proof_ref строка }
тип OwnerIntent { intent_id строка, epic_id строка, revision число, result_ref строка, question строка, deadline число, idempotency_key строка }
```

## Данные хозяина

| Имя | Тип | Инвариант / назначение |
|---|---|---|
| работы | `[]Работа` | Стабильный id и отдельная ревизия/состояние для каждого узла |
| contains | `[]Ребро` | Рекурсивное включение; общий граф вместе с зависимостями ацикличен |
| depends | `[]Зависимость` | Связь потребителя с производителем и конкретным принятым pin |
| журнал | `[]Событие` | Упорядоченный, дописываемый журнал с id события и ожидаемой ревизией |
| intent | `?OwnerIntent` | Единственное восстанавливаемое намерение текущей сдачи; до доставки не означает `WaitingOwner` |
| решение | `?OwnerDecision` | Применяется лишь при корректных intent id, ревизии и доверенном proof |
| blockers | `[]строка` | Независимые pause/stop, stale, owner, safety и unknown-effect блокировки; снимаются адресно |

## Стороны и граница эффектов

| Сторона | Тип | Может | Не может |
|---|---|---|---|
| хозяин | `machine хозяин` | Проверить ревизию/guards, записать событие, пересверить pin, собрать итог детей | Сам удостоверить волю владельца или объявить внешний эффект состоявшимся без receipt |
| исполнитель ребёнка | `agent(итог РезультатРебёнка)` | Предложить результат и ссылки на доказательства | Изменить родительский журнал, pin или owner gate |
| доверенный источник владельца | `human` | Передать коррелированное решение и proof | Решить иной intent/revision |
| адаптер доставки | `функция доставить(итог OwnerIntent) -> Receipt` | Выполнить intent доставки и сообщить receipt/unknown | Создать новое намерение при рестарте или превратить unknown в success |

**Контраст:** локальный переход — проверка входа и атомарная запись состояния/события хозяином. Эффектная граница начинается только после сохранения intent; доставка, подтверждение и неизвестный исход принадлежат host/адаптеру. Эта модель не выполняет эффект и не обещает exactly-once.

## Внешние функции

Вида `effect` у сторон нет; внешний эффект доставки выполняет host через функцию ниже (класс действующая: внешнее действие, результат не гарантирован, исход бывает неизвестен).

| Функция | Сигнатура | Класс |
|---|---|---|
| доставить | доставить(итог OwnerIntent) -> Receipt | действующая |

## Допустимые события и исходы

| Событие | Guard хозяина | Запись / исход |
|---|---|---|
| `ChildChanged` | Ребёнок — член графа; revision ожидаемая | Записать событие; сохранить прежние pins; затронутые зависимости пометить stale, независимые ветви не менять |
| `ArtifactAccepted` | Производитель и этап существуют; есть proof принятия | Записать неизменяемую версию; существующие pins автоматически не передвигать |
| `PinReconciled` | Новый артефакт принят; старый pin совпадает; причина, proof и полномочие валидны | Заменить только названный pin; адресно пересчитать зависимых потребителей |
| `OwnerIntentRecorded` | Все обязательные дети/этапы готовы к сдаче; blocker set пуст; revision актуальна | Сначала устойчиво сохранить тот же intent id, result ref, срок и ключ идемпотентности; состояние `DeliveryPending` |
| `DeliveryConfirmed` | Receipt соответствует сохранённому intent id | Зафиксировать receipt; `WaitingOwner`. Повтор receipt возвращает прежний исход |
| `OwnerDecisionReceived` | Тот же intent/revision; решение typed; trusted proof проверен | `Accept` завершает только если blockers пусты; `Return` оставляет работу нетерминальной; `Reject` завершает revision как `Failed` |
| `RestartRecovered` | Снимок/журнал читаемы и согласованы | Восстановить тот же граф, pins, blockers, журнал и intent; недоставленный intent продолжить с тем же id, неизвестный исход не повторять вслепую |

Любое событие с неизвестным типом, повторным id, неверной expected revision или неисполненным guard отвергается до изменения данных; повтор известного id возвращает ранее сохранённый исход. Terminal revision не переписывается: дальнейшая работа — новая revision или отдельный полномочный reopen.

## Агрегированное принятие

Итог эпика вычисляется из его зафиксированного графа, а не из сообщения ребёнка: каждый обязательный потомок terminal-success, каждый обязательный этап имеет принятый артефакт, каждый dependency pin ссылается на точную принятую версию, stale/blocker set пуст, а owner intent относится к текущей revision. Только затем хозяин записывает intent общей сдачи. Даже после доверенного `Accept` хозяин отмечает эпик `Completed` лишь при совпадении intent/revision и отсутствии blockers. `Return` сохраняет журнал и допускает исправление/повторную сдачу; `Reject` — terminal `Failed`. Несогласованная или неполная ветвь оставляет агрегат незавершённым; независимая ветвь и её pins не сбрасываются.

## Минимальные пробы (контрактные, не runtime-тесты)

| Проба | Действие | Ожидаемый результат |
|---|---|---|
| Вложенность | `E0 contains E1, T2`; `E1 contains T1, T3`; `T3 depends(T1, build/V1)` | Узлы сохраняют отдельные id/revision/journal; mixed cycle отвергается до изменения графа |
| Pin и рестарт | Принять `build/V2`, рестарт до reconcile | `T3` всё ещё закреплён за V1; рестарт восстанавливает тот же pin; только адресный `PinReconciled` переводит на V2 |
| Owner intent и рестарт | Записать intent Q, остановить до receipt, восстановить хозяина | Восстановлен тот же Q/id/key; до receipt состояние не `WaitingOwner`; повторная доставка не создаёт второй intent |
| Aggregate gate | Один обязательный потомок stale или не принят; затем разрешить stale и получить trusted Accept | Первая сдача отвергнута без эффекта; позднее агрегат принимается только по тому же актуальному intent/revision и полному набору guards |

Проба последней строки проверяет контрактную логику хозяина; доверие к источнику решения и реальный delivery receipt остаются внешними предусловиями, а не доказательством внутри модели.
