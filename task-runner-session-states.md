# Запуск сессии: стейт-машина

Запуск одной сессии агента — ворота профиля и цены (В2), проверка объёма (ОБЪЁМ, В1), обращение к агенту (СЕССИЯ) и ворота сбоя (В13), — записанный состояниями и переходами по [state-machine-spec.md](state-machine-spec.md): обращения к внешним сторонам идут по контракту обращения (правила 15–22), общие события — правила 23–24 (ПАУЗА и общие события — подключаемый фрагмент, правило 36), машина вызывается из другой машины как сторона запроса (правило 35). **Первоисточник — этот файл.** Ранее написанная схема — алгоритм `run` и ворота `gate(В1, В2, В13)` псевдокода [task-runner-pseudocode.md](task-runner-pseudocode.md): она устарела (2026-10-17), сохранена без правок и с этим файлом не сверяется (владелец, 2026-10-18: перевести алгоритм раннера в форму состояний, как совещание, не приводя псевдокод к контракту); «Решения при переводе» и «Откуда в псевдокоде» (перечень происхождения) — в конце. Эту цепочку раньше повторяли копией раннер ([task-runner-states.md](task-runner-states.md)) и проверка цикла ([task-runner-review-states.md](task-runner-review-states.md)); теперь она одна, и обе машины зовут эту как вложенную (владелец, 2026-10-18: «Шаг 5, 6 — делай»). Словарь, ворота В1, В2, В13, профили запуска и форматы файлов — [task-runner.md](task-runner.md); коды сессий — [task-sessions.md](task-sessions.md); движок — [state-machine-engine-automaton.md](state-machine-engine-automaton.md).

Опытный режим: раннером не выполняется — раннер исполняет псевдокод.

**Что машина добавляет к ранее написанной схеме** (раннер пока исполняет псевдокод и этого не делает): сигналы человека «стоп человека» и «продолжить» вне ворот (состояние ПАУЗА), вызов этой машины из верхней с событием «отмена_запроса» (правило 35 спецификации); запуск сессии стал вложенной машиной с ответом из любого конца, а не функцией, возвращающей значение.

**Отличия от ранее написанной схемы:** все отличия поведения от псевдокода перечислены в разделе «Решения при переводе» этого файла (перенесены из раннера и проверки цикла: повтор В13 без нового В2, исходы В1 и В2) и в «Решениях при переводе» [task-runner-states.md](task-runner-states.md); отдельного списка здесь нет.

Все переменные раздела «Переменные машины» сохраняются целиком: после перезапуска исполнитель входит заново в «состояние» (правило 22). Переменные меняются только в столбце «Что меняется»; исключения — механика контракта («запрос_вызова», «открытые_запросы», «принятые_запросы», счётчики попыток, «При приёме», запись принятого результата — правила 14, 15, 21) и «состояние» (правило 13). Объекты раздела «Внешние объекты» (кроме задания и входа вызова) — хранилище: их пишет исполнитель при приёме ответа роли; роль возвращает результат и в хранилище машины не пишет (правило 8). Значения `""`, `[]`, `0`, `нет` и знак «+» — правило 30.

Служебные хранилища исполнителя — расшифровки диалогов, префиксы кеша, записи запусков, подсказка профиля, выбранные профили по фазам, учёт токенов, режимы ворот — не данные машины: ни одно условие и ни один шаг их не читает (правило 11); они общие у верхней и вложенных машин одной задачи. Что с ними делает запуск сессии — «Реализация на файлах» этого файла.

Константы и параметры: нет. Срок бездействия обращений этой машины не задан: в раннере его задаёт только совещание; поле запроса — `0`, исполнитель «нет ответа» не порождает.

## Типы

Строка — одно поле. У составного типа имя стоит в первой его строке; у типа с вариантами — «Тип (вариант)». []T — список значений типа T. Исход ворот — слово ворот из перечня в строке события; тип отдельно не заводится. Примеры выдуманы и показывают форму; у поля с перечнем значений — пример на каждое значение. Подробность типов — по правилу 6 [state-machine-spec.md](state-machine-spec.md): тексты и ссылки на файлы — Текст, потому что машина по ним не ветвится. Запрос и Ответ — конверт контракта обращения (правила 15 и 16), одинаков для всех обращений; T и R — «Вход» и «Выход» состояния. Типы `Находка`, `Артефакт` и `ИтогСессии` объявлены один раз в [task-runner-states.md](task-runner-states.md), «Типы» и «Типы на Нове»; здесь объявлены `Свод`, `ВходЗапускаСессии` и `ИтогЗапускаСессии` (их используют вызывающие машины: [task-runner-states.md](task-runner-states.md) и [task-runner-review-states.md](task-runner-review-states.md)). **Где разбирается значение перечня.** `ИтогСессии`: по нему ветвятся вызывающие машины (ПОСЛЕ_СЕССИИ, ИТОГ_ПРАВКИ), эта машина его только возвращает; `Находка` и `Свод` она не читает вовсе — это данные файла проверки, которые она передаёт вызывающей машине. Блок «Типы на Нове» после таблицы — те же типы на языке Нова (https://github.com/nv-lang/nova): Число — `int`, Текст — `str`; это одна из возможных записей, машина от неё не зависит.

### Типы на Нове

```
/// Свод
type Summary { k int, p int }

/// ВходЗапускаСессии
type SessionLaunchInput { session str, source Option[str], phase Option[str], launch_pass Option[int], task_dir str, repo_dir str, delivery_mode str, route str, source_list Option[str], delivery_short bool }

/// ИтогЗапускаСессии
type SessionLaunchResult { result SessionResult, summary Option[Summary], findings Option[[]Finding] }
```

Тип `ОбъёмЗапуска` в коде — текст «помещается» или «не помещается» (`объём_запуска()` слоя методики). Остальные типы блока объявлены один раз в [task-runner-states.md](task-runner-states.md), «Типы на Нове», и здесь не повторяются: `Finding`, `Severity`, `Level`, `SessionResult`. Конверт контракта обращения — в движке ([state-machine-engine-automaton.md](state-machine-engine-automaton.md), раздел «Типы»). Поле `launch_pass` — номер захода (`заход_запуска`); у вызова из раннера его нет.

Там, где итога свода может не быть, — `Option[Summary]`.

## Инварианты

1. **Решает только человек** — на воротах этой машины (В1, В2, В13, ПАУЗА), а сигналом «стоп человека» — в любой момент; исполнитель считает, переключает состояния и пишет журнал. Исключение — ворота В2, которые человек перевёл в режим «показывать и продолжать» (`task-runner.md`, «Ворота»); исход по умолчанию даёт исполнитель этой машины и пишет его в журнал. Эти ворота — ворота вложенной машины для раннера и проверки цикла: у вызывающей машины они не повторяются.

## Общие события

Описаны здесь один раз и в таблицах состояний не повторяются (правило 23: порядок разбора, ПАУЗА, отбрасывание лишних сигналов); общие события, состояние ПАУЗА и передача сигналов вложенным записаны фрагментом «Пауза» — один раз для всех машин (правило 36 спецификации).

**Подключает фрагмент «Пауза»** ([state-machine-pause-states.md](state-machine-pause-states.md)); параметры: слово остановки — «остановить»; вложенные — вложенных машин нет (агент и человек — стороны запросов, не машины); отмена запросов — запрос к агенту отменяется, группа процессов агента останавливается; вход заново — ничего; право записи — право записи на файлы задачи. Фрагмент вносит в машину состояние ПАУЗА (обращение к человеку), общие события «стоп человека», «стоп от родителя», «отмена_запроса» и события ПАУЗЫ; значения «остановка» «ПАУЗА: остановить» и «отмена_запроса» есть в таблице «конец → ответ» раздела «Контракт машины».

## Контракт машины

Запуск сессии вызывают из верхних машин как сторону запроса — из раннера и из проверки цикла; правила — [state-machine-spec.md](state-machine-spec.md), правило 35. Запрос — `Request[ВходЗапускаСессии]`, ответ — `Response[ИтогЗапускаСессии]` (`Answer` либо `Refusal`); машина отвечает ровно один раз. Исход сессии, который раньше возвращала функция `run`, разложен по ответу: сессия отработала (в том числе остановилась словом «вопрос», «план», «требования» или «ревизия») — `Answer` с `итог_сессии`; запуск не состоялся — `Refusal` (человек остановил на воротах, сессия не дала результата, запуск отменён).

## Состояния

Раздел на каждое состояние; виды и правила формы — [state-machine-spec.md](state-machine-spec.md).

Четыре вида состояний:

- **обращение** — машина просит о чём-то роль или человека и ждёт ответа (пример: СЕССИЯ — просит агента выполнить сессию);
- **операция** — машина сама делает внутреннюю работу, ни у кого ничего не спрашивая (в этой машине операций нет);
- **развилка** — машина смотрит на свои данные и выбирает дорогу, ничего больше не делая (пример: ОБЪЁМ — помещается ли диалог сессии в предел входа);
- **конец** — запуск закончен, дальше машина не идёт (пример: КОНЕЦ — итог сессии возвращён).

Начальное состояние — В2.

### В2 — обращение

*Показывает человеку профиль запуска сессии и оценку цены и просит подтвердить, чтобы дорогой запуск не начинался без него. Вход в запуск любой сессии.*

При входе: ворота В2: профиль запуска (класс модели, усилие, размышление, бюджет), выбранный по умолчаниям фазы и подсказке агента из прошлой сессии (`task-runner.md`, «Профили запуска»), и оценка цены по токенам слоёв; при расшифровке диалога автора больше примерно вдвое слоёв 0–3 человек выбирает, продолжать диалог или начать новый; совет ниже по классу или усилию показывается всегда. В режиме «показывать и продолжать» (профиль равен умолчанию) исполнитель сам даёт исход «подтвердить» и пишет это в журнал. Выбор профиля и подсказка — механика запуска (служебные хранилища), в данные машины не входят.

## Реализация на файлах

Один из вариантов — раннер `task-runner.md` (исполняет псевдокод, а не эту машину); таблица сопоставляет имена машины с именами реализации, а контракт, фиксацию и приём ответа определяют правила 13, 14 и 18 спецификации. Другая реализация может хранить те же объекты иначе (база, очередь, память процесса) и передавать запросы иначе, машина от этого не меняется (правило 4). Служебные хранилища (профили по фазам, подсказка, префиксы, расшифровки, учёт токенов, режимы ворот), состояние и шаг — в [task-runner-states.md](task-runner-states.md), «Реализация на файлах»; вызывающие машины — раннер и проверка цикла — передают в запросе вход и получают итог ответом.

|---|---|

| рабочая копия попытки | роль «агент» правит файлы задачи сразу (как раннер), а не копию: проверка «предложение не менялось с начала попытки» здесь не применяется (правка человека в простое возможна), приём по `state-machine-spec.md` правило 14 не отличает файлы агента от копий; полная реализация может завести `*.attempt-<сторона>-<попытка>.md` |

Транспорт обращений — варианты, не нормы (правило 20):

| Транспорт | Для каких обращений подходит | Что даёт по контракту |
|---|---|---|
| файлы и запуск процесса (как в раннере) | агент: сессии по одной | идентификатор — запись запуска и файл артефакта; ответ — артефакт и итоговая строка `progress.log`; сбой — коды формы, отсутствия артефакта, отказа модели |

| вложенная машина как процесс или вызов функции | сам запуск сессии для вызывающих машин | идентификатор запроса и ответ по правилу 35; сигналы вниз получают только от вызывающей машины |

## Решения при переводе

Владелец поручил перевести псевдокод в форму состояний, не приводя его сначала к контракту (владелец, 2026-10-18). Места, где псевдокод неоднозначен, непоследователен или нарушает контракт, решены так (решение — по контракту [state-machine-spec.md](state-machine-spec.md)); решения по раннеру — в [task-runner-states.md](task-runner-states.md), по проверке цикла — в [task-runner-review-states.md](task-runner-review-states.md). Перенесены сюда: решение 1 (прежние 5 раннера и 6 проверки цикла), 2 (прежнее 6 раннера), 3 (часть прежнего 8 раннера: исходы В1 и В2), 4 (прежнее 7 раннера); решения 5–8 новые: цепочка запуска сессии теперь записана один раз.

1. **Запуск сессии — вложенная машина, а не цепочка состояний в каждой вызывающей машине.** В псевдокоде `run` — одна функция, вызываемая отовсюду; в прежнем переводе цепочка В2 → ОБЪЁМ → В1 → СЕССИЯ → В13_СЕССИЯ стояла копией в раннере и в проверке цикле (вложенная машина не может пользоваться состояниями родителя, правило 35, пункт 7). Теперь у неё свой вход, выход и таблица «конец → ответ», и обе машины зовут её обращением ЗАПУСК_СЕССИИ. **Место вызова называет вызывающая машина.** Метка «продолжение» осталась в вызывающей машине: она не входит ни в вход запуска, ни в его итог, потому что «куда после сессии» — разбор итога сессии в её собственном состоянии ПОСЛЕ_СЕССИИ (переход «куда» из переменной запрещён, правило 24); нужное вызывающей машине из итога — `итог_сессии`, а у сессий проверки ещё итоговая строка и находки захода. *Почему:* 15 мест вызова `run` раннера и 4 места проверки без метки дали бы столько же копий ворот и ожидания; одна машина — одна правка.
2. **`run` «не возвращает ошибок»** (псевдокод: В13 внутри). В машине сбой — событие, В13 — состояние В13_СЕССИЯ; «повторить» — «запуск заново» того же запроса (правило 18), а не новый `run` целиком с В2 (в псевдокоде повторный `run` заново выбирал бы профиль и стирал подсказку). Ветка «бездействие дольше срока → В13» (`run`, строка 239) вне совещания не возникает: срок бездействия там задан только совещанию, у запроса к агенту он `0`. **Это правка поведения псевдокода:** он при «повторить» запускал `run` заново целиком. Она выведена из `task-runner.md`: раздел «Ворота», В13 («повторить или остановить программу» — повторяется сессия, а не выбор профиля), раздел «Профили запуска», абзац «Подсказка агента» (подсказка «действует на один следующий запуск и стирается после него»; повторный `run` выбрал бы профиль без неё) и В2 («перед каждой сессией»: повтор той же сессии — не новая сессия). *Почему:* контракт требует событие «сбой» и отмену прежнего запроса (правило 18); повтор не должен второй раз спрашивать профиль, уже подтверждённый.
3. **Исходы ворот В1 и В2 в источниках не перечислены** — взяты по тому, что псевдокод делает за воротами: для В2 один исход «подтвердить»; для В1 — «повторить» и «остановить», как у В13. *Почему:* строка таблицы нужна на каждый исход ворот (правило 28), а ворота без исхода — неисполнимая машина; список закрыт, расширять — менять файл. **Требует слова владельца**, если исходы должны быть другими.
4. **Профиль, подсказка, префикс, расшифровка, запись запуска, учёт — не данные машины.** `choose_profile`, `state.hint`, `profile_by_phase`, `build_prefix`, `keep_alive`, `state.transcript`, `state.launches`, `state.running`, `record_usage`, `check_cache` отнесены к механике запуска и служебным хранилищам исполнителя; ворота В2 и В1 остались состояниями, потому что решает человек. *Почему:* ни одна развилка не ветвится по ним (правило 6); владелец велел модельные подробности держать в «Реализации» (2026-10-18).
5. **«Остановить» на В1 и В13 — отказ запуска, а не остановка раннера.** В псевдокоде `run` «останавливает группу процессов агента и выходит из программы». Запуск сессии — вложенная машина: он кончается `Refusal` с кодом `StoppedByHuman` (ОСТАНОВЛЕНО), а раннер или проверка цикла остановятся сами (их состояние ОТКАЗ_СЕССИИ). Различие слов «В1: остановить» и «В13: остановить» остаётся в журнале и в `остановка` этой машины; вызывающие машины записывают «запуск сессии: остановлено человеком» и в своём журнале различия не хранят (решение с причиной: движок передаёт родителю только код сбоя, текст отказа в событие не входит, а различие слов ничего не меняет в маршруте). **Новый путь сбоя:** ОШИБКА этой машины (дефект цепочки запуска) раньше была ОШИБКОЙ самой вызывающей машины, теперь это отказ `NoResult`, который вызывающая машина разбирает в ОТКАЗ_СЕССИИ и заканчивает ОСТАНОВЛЕНО с `остановка` «запуск сессии: нет результата» (ответ вызвавшему — `Refusal`/`NoResult`, как раньше, но состояние конца другое). *Почему:* контракт требует ответ с кодом из закрытого списка (правило 35, пункт 6): внутренние сбои наружу не вытекают.
6. **Свод и находки захода возвращаются с итогом.** Сессия проверки пишет файл захода; итоговую строку и находки при приёме ответа записывает исполнитель вызывающей машины в её хранилище (правило 14), поэтому они входят в «Выход» ответа (`свод`, `находки_проверки` — только у сессий проверки цикла). *Почему:* прежняя СЕССИЯ проверки цикла возвращала их в своём «Выходе»; после выделения машины запуска они остаются тем же результатом того же запроса, а не данными вызывающей машины, пока ответ не принят.
7. **`заход_запуска` и `фаза` необязательны.** У вызова из раннера нет номера захода (сессии С1…С9 не пишут файл захода), у вызова из проверки цикла нет фазы (профиль выбирается по коду сессии). *Почему:* один тип входа на обе вызывающие машины; обязательность по вызывающей машине не выражается типом (правило 6), поэтому необязательные поля помечены в таблице «Вход».
8. **Перезапуск: запрос к вложенной машине повторяется, а не отменяется (уточнение правила 22).** Правила 22 и 18 отменяли открытые запросы умершего исполнителя; для запросов к вложенным машинам спецификация теперь делает исключение (правило 22; правило 35, пункт 4): после перезапуска вызывающая машина повторяет запрос ЗАПУСК_СЕССИИ с тем же идентификатором, а запуск сессии возобновляется из своего сохранённого состояния (В2, В1, СЕССИЯ, В13_СЕССИЯ или ПАУЗА); отменяется только запрос этой машины к роли «агент» без принятого ответа, и сессия идёт заново отправкой того же запроса (входом в СЕССИЮ). *Почему:* так уже сделано в движке (`возобновить`), а без исключения вложенный запуск, давший профиль и подтверждение В2, спрашивал бы их снова.
9. **Поля маршрута во входе вызова.** `ВходЗапускаСессии` получил `маршрут`, `перечень_источников` и `сдача_сжата`: промпты быстрого маршрута читают источники только по перечню и знают, что plan.md нет, а сдача может быть сжата (слово владельца, 2026-10-18; [task-runner-states.md](task-runner-states.md), решения 27–52). Три числа цикла (потолок заходов, чистые заходы, пробы) эта машина не читает и не получает: ни одна её строка по ним не ветвится (правило 6). `перечень_источников` необязателен: проверка цикла его не передаёт (проверяющий читает широко, чтобы не оказаться зависимым от списка автора), а у полного маршрута перечня нет. *Почему:* шаг читает только свой вход (правило 11), а подстановки собирает исполнитель по входу запроса; поле «маршрут» нужно, чтобы строку про plan.md получали и сессии, запущенные проверкой цикла.
