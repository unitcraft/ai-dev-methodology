# Стартовый комплект стражей

Стражи — программы, которые проверяют репозиторий до коммита, до пуша и на сервере CI: секреты и пути
машины, запрещённые имена, порчу текста, битые ссылки, форматы документов, сообщения коммитов. Комплект
сложился на живом проекте и обобщён: имён, номеров правил и форматов того проекта в нём нет, всё, что
зависит от проекта, вынесено в один файл параметров `scripts/guards/guards.conf`.

Папка повторяет дерево нового проекта один к одному: установка — копирование её содержимого в корень
проекта. Два файла лежат иначе. **Этот README в новом проекте лежит в `docs/guards.md`** (в корне у проекта
свой README): шапки стражей, подсказки разборщика параметров и комментарии `guards.conf` ссылаются на него
как «docs/guards.md (README комплекта), «раздел»»; в комплекте это тот же файл под именем `README.md`.
Относительных ссылок в нём нет, поэтому перенос в `docs/` их не ломает. **`verify-portability.sh` в новый
проект не копируется**: это инструмент осмотра комплекта до установки (раздел «Приёмка переносимости»).

## Состав

```

scripts/guards/guard-secrets.py   страж секретов и путей машины (индекс, коммит, дерево)
scripts/guards/guard-commit-message.py   страж сообщения коммита
scripts/guards/run-all.sh         общий запуск стражей check-* и счёт вердиктов
scripts/guards/commit-range.sh    какие коммиты пуша судить (pre-push и CI)
scripts/guards/ci-mask.sh         маскирование списка имён в журнале CI
scripts/guards/prove-red.sh       «доказательство красного»: заглушка вместо стража роняет его самотест
scripts/guards/probe-empty-root.sh   пустота не бывает чистой: ни одного «ок» на пустом корне

scripts/guards/selftest/          самотесты: по одному на каждого стража, хук и запускающий скрипт
scripts/guards/probe/             шаблон пробы журнала CI (не задание: копируется руками)
scripts/githooks/                 хуки git: pre-commit, commit-msg, pre-push
scripts/agent-hooks/guard-git.py  хук ИИ-агента на команды оболочки (подсказка против опасного git)
scripts/install-hooks.sh          установщик хуков git
.github/workflows/guards.yml      задание CI: стражи, самотесты, доказательство красного, пустой корень
.claude/settings.json             запись хука агента (PreToolUse на Bash и PowerShell)
.gitattributes                    концы строк LF для скриптов, хуков и настроек

verify-portability.sh             приёмка переносимости; в новый проект не копируется
```

## Установка

Без установщика хуки git не работают: git не берёт их из репозитория сам. Шаги:

1. Скопируйте содержимое папки комплекта, кроме `README.md` и `verify-portability.sh`, в корень проекта;
   `README.md` положите в `docs/guards.md`.
2. Заполните `scripts/guards/guards.conf` (раздел «Параметры проекта»). Обязательные ключи без
   значения дают красный вердикт с подсказкой, а не чужое значение по умолчанию. Поставляемые значения
   обязательных ключей — предложения, а не решение за проект (там же, «Из коробки»): просмотрите и смените их.
3. Заведите список запрещённых имён вне репозитория: файл из `PRIVATE_NAMES_FILE` (по умолчанию
   `~/.config/guards/private-names.txt`), образец на строку, решётка — комментарий. В CI — секрет с именем
   из `PRIVATE_NAMES_VAR` (заводится в настройках CI хостинга кода).
4. Добавьте файлы в git с битом исполнения у хуков и скриптов sh (на машине без битов исполнения в файловой
   системе git его сам не поставит): `git add -- scripts .github .claude .gitattributes docs/guards.md`, затем
   `git add --chmod=+x -- scripts/githooks/* scripts/*.sh scripts/guards/*.sh scripts/guards/lib/*.sh scripts/guards/selftest/*.sh`.
5. Подключите хуки: `sh scripts/install-hooks.sh`. Установщик пишет `core.hooksPath` и, если политика
   сверяет адрес автора, ожидаемый адрес в ключ `EXPECTED_EMAIL_KEY`; повтор ничего не меняет, чужая
   настройка — громкий отказ (флаг `--reset` заменяет её).
6. Проверьте: `python scripts/guards/check-wiring.py` («ок: осмотрено N стражей»), `sh scripts/guards/run-all.sh`
   (итог без FAIL), `sh scripts/guards/selftest/run-selftests.sh`, `sh scripts/guards/prove-red.sh`,
   `sh scripts/guards/probe-empty-root.sh`.

Нужны git, sh и Python 3.9 или новее (только стандартная библиотека). Интерпретатор ищется запуском
(`python`, `python3`, `py -3`): на машине разработчика `python3` бывает заглушкой.

## Приёмка переносимости

`verify-portability.sh` лежит рядом с этим README и в новый проект не копируется: им проверяют сам комплект
до установки (тот, кто его правит или принимает). Запуск: `sh verify-portability.sh` из папки комплекта или
по пути к ней. Комплект берётся из закоммиченного HEAD (`git archive` папки комплекта); `--worktree` — из
рабочей копии, `--only <начало имени>` — один кейс, `--full` — в честном кейсе ещё самотесты и
доказательство красного (долго).

Каждый кейс — свежий репозиторий во временной папке без файлов источника: комплект ставится по шагам
«Установки» (копия, `docs/guards.md`, биты исполнения, установщик хуков, первый коммит через хуки), список
имён и образцы нарушений выдуманы и собираются при прогоне. Кейсы:

- честный вход — зелёный: коммит и пуш в пустой удалённый репозиторий через хуки, стражи как в CI,
  мета-проверка, пустой корень, ссылки файлов проекта на `docs/guards.md` ведут в существующие разделы;
- секрет, путь машины, запрещённое имя — красный коммит с адресом и правилом, без значения;
- храповик: подмена нарушения при том же счёте, откат исправленного без записи, исправленное с оставленной
  записью — красные;
- потерянная мишень (папка задач, база храповика) — красный, а не «ок»;
- убранный обязательный ключ — красный с подсказкой;
- из коробки — зелёный, храповик «судить нечего»;
- таблица «Параметры проекта» совпадает с ключами, которые разбирает `scripts/guards/lib/conf.py`
  (обязательность и умолчание).

Вывод — таблица «кейс -> вердикт» и итог «ок: приёмка переносимости: кейсов N, расхождений 0»; любое
расхождение — `FAIL` с названиями кейсов и выводом их команд.

**Почему.** Самотесты гоняют стражей рядом с исходником комплекта и не видят, что новый проект получает
не то: забытый в копии файл, ссылку на путь источника, первый пуш, который хуки не пропускают. Так
наблюдалось при первой приёмке: первый пуш нового проекта в пустой удалённый репозиторий хук pre-push
отклонял с подсказкой «сначала git fetch», хотя получать было нечего.

## Параметры проекта

Файл `scripts/guards/guards.conf`: строки `КЛЮЧ=значение`, решётка первым знаком — комментарий, кавычки не
нужны. Неизвестный ключ (опечатка), повтор ключа (кроме `TASK_DOC_RULE` и `RATCHET_GUARD`), пропавший обязательный ключ и
значение не по форме — красный вердикт с подсказкой, какой ключ и что в нём писать. Файл читает один
разборщик `scripts/guards/lib/conf.py`; скрипты sh и задание CI зовут его как `python scripts/guards/lib/conf.py get <КЛЮЧ>`,
проверка всего файла — `python scripts/guards/lib/conf.py check` и мета-проверка `check-wiring.py`.
Переменная окружения `GUARDS_CONF` подменяет путь к файлу (ею пользуются самотесты).

Значения по умолчанию есть только у ключей раскладки и у ключей, где комплект ничего не решает за проект:
они повторяют раскладку самого комплекта. Всё, что выбирает проект (имена, ветка, политика, форматы), —
обязательные ключи.

**Из коробки.** Поставляемый `guards.conf` заполняет обязательные ключи, чтобы комплект был зелёным сразу
после установки. Это предложения, а не умолчания: строка, убранная из файла, даёт красный вердикт, а не это
значение. В файле они помечены «ПРЕДЛОЖЕНИЕ» и повторяют выбор проекта-источника:

- `MAIN_BRANCH=main`;
- `PRIVATE_NAMES_VAR=GUARDS_PRIVATE_NAMES`, `PRIVATE_NAMES_FILE_VAR=GUARDS_PRIVATE_NAMES_FILE`,
  `PRIVATE_NAMES_FILE=~/.config/guards/private-names.txt` (меняя имя переменной, поменяйте его и в задании CI);
- **политика коммитов из коробки — строгая политика проекта-источника, смените её под проект:**
  `COMMIT_SIGNOFF=required` (строка Signed-off-by автора в каждом коммите), `COMMIT_FORBIDDEN_TRAILERS=Co-authored-by`,
  `COMMIT_ASCII_ONLY=yes`, `COMMIT_AUTHOR_EMAIL_CHECK=yes`; без этих требований —
  `COMMIT_SIGNOFF=off`, `COMMIT_FORBIDDEN_TRAILERS=none`, `COMMIT_ASCII_ONLY=no`, `COMMIT_AUTHOR_EMAIL_CHECK=no`;
- `AGENT_HOOK_RULES` — все правила хука агента (`none` выключает все).

Ключи форматов (`TASK_DOC_RULE`, `STATUS_TABLE_TASK_PATH`, `TEST_FILES`) и `RATCHET_GUARD` поставляются со
значением `off`: форматы и долг проекта комплект не знает. **Почему:** ожидаемая ошибка — проект, получивший
заполненный файл, принимает чужую политику за требование методологии и не замечает, что выбор был за ним.

Пути и имена, которые CI и настройки агента не могут прочитать из файла параметров, записаны в них явно:
папка стражей в хуках git, установщике, задании CI и команде хука агента; имя секрета списка в задании CI;
путь к `guards.conf` в команде хука агента. Меняя раскладку или имя переменной, поменяйте и эти места:
`check-wiring.py` сверяет их с ключами и краснеет на расхождении.

Значение `off` у ключей формата — решение проекта «правило не нужно»: страж печатает «судить нечего» и
называет ключ. Это не пропуск: в CI «судить нечего» зелёное, «пропущено» — красное.

## Договор стража

Вызов: `<страж> [--root <папка>] [--index | --commit <хеш>] [--ci]`. Источник по умолчанию — рабочая копия
и список `git ls-files`; `--index` — индекс (временный индекс `git commit --only` соблюдается); `--commit` —
файлы, изменённые коммитом. Вердикт — последняя строка вывода, одна из четырёх форм: «ок: осмотрено N
<мишень>», «судить нечего: <причина>», «пропущено: <причина>», «FAIL: ...» с кодом 1. Нарушение печатается
с адресом «файл:строка: правило: описание», без значения секрета или имени. Нет git, интерпретатора,
списка имён или параметра — «FAIL: предпосылка» с подсказкой, а не пропуск. Новый страж `check-*`
подключается построением: `run-all.sh` запускает всех по маске.

Исключение по строке — пометка с причиной в комментарии на той же строке: `guard-allow(<правило>): <причина>`
(стражи ссылок и гигиены текста); для файла, где предмет проверки — сам байт, — `guard-fixture(<правило>): <причина>`.
Пометка без причины — красный; принятая пометка печатает причину. Исключить папку или маску нельзя.

**Почему.** Ожидаемая ошибка без договора: разные формы «ок» и коды возврата, общий запуск не может их
сосчитать, а страж, молча пропустивший проверку, неотличим от зелёного.

## Правила, которые держат стражи

### Секреты и пути машины

`guard-secrets.py`: маркер конфликта слияния, заголовок приватного ключа, токены доступа двух
распространённых хостингов кода по известным префиксам, логин и пароль внутри адреса, непустой пароль
в присваивании, путь машины (буква диска с двумя папками, домашний каталог с именем пользователя;
определение одно на всех — `lib/machine_paths.py`). В индексе и коммите судятся добавленные строки, в
дереве (CI) — весь файл по правилам высокой уверенности. **Почему:** секрет или путь, попавший в
публичную историю, без силового пуша не вычистить.

### Запрещённые имена

`check-private-names.py` и страж сообщения: образцы из списка вне репозитория (подстрока без учёта
регистра) не встречаются в файлах, путях файлов и сообщениях коммитов. Вывод называет номер образца, не
значение; в CI значения маскируются в журнале (`ci-mask.sh`). Нет списка, он пуст, в UTF-16 — красный с
подсказкой. **Почему:** имена приватных проектов и заказчиков общий образец не видит; в проекте-источнике
наблюдалось, что список с концами строк CRLF несколько недель молча не находил ни одного имени, — поэтому
отсутствие и порча списка красные.

### Чистый текст

`check-text-hygiene.py`: управляющие байты, NUL, UTF-16, кракозябры (UTF-8, прочитанный как CP1251),
символ замены U+FFFD, BOM, смешанные концы строк — в любом файле вне списка бинарных расширений. **Почему:**
порча не видна глазами в обзоре, но ломает поиск, ссылки и сравнение.

### Ссылки между документами

`check-md-links.py`: относительная ссылка в `.md` ведёт на существующий в источнике файл или папку внутри
репозитория, якорь совпадает с заголовком. **Почему:** перенос папки молча ломает ссылку, читатель
попадает в пустоту.

### Формат документов задач

`check-task-docs.py` судит машинные места документов по правилам `TASK_DOC_RULE`; формат комплект не
выдумывает. Правило: `<вид> <образец пути> <образец строки>`; образец пути — без пробелов (пробел
пишется `\x20`), образец строки — остаток строки. Виды: `first-line` — первая строка файла подходит под
образец; если у образца пути и у образца строки есть группа `(?P<n>...)`, числа в них равны (номер захода в
имени файла и в строке); `every-line` — каждая непустая строка подходит; `unique` — значение в начале
строки (группа `id` или всё совпадение) не повторяется в файле. Образец строки прикладывается с начала
строки; чтобы требовать строку целиком, закончите его `$`. В `guards.conf` закомментированы примеры форм
из документов методологии (task-sessions.md и task-runner.md): статус в первой строке spec.md и plan.md,
итог захода в файлах проверки, строки журнала хода progress.log. **Почему:** программа цикла читает эти
места; молча испорченная первая строка запускает проверку заново поверх утверждённого документа.

### Список задач руками не ведётся

`check-no-status-table.py`: в `.md` нет таблицы с колонкой состояния, у которой первая ячейка — ссылка на
папку задачи (образец `STATUS_TABLE_TASK_PATH`). **Почему:** таблица «задача — статус», набранная руками,
расходится с папками задач и становится ложью.

### Тест без проверок

`check-tests-have-checks.py`: каждый файл под образцом `TEST_FILES` содержит хотя бы одну проверку
(`TEST_CHECK`) вне комментариев (`TEST_COMMENT`). **Почему:** тест без проверок всегда зелёный и создаёт
ощущение покрытия.

### Храповик долга

`check-ratchet.py` оборачивает стражей `check-*`, названных в `RATCHET_GUARD`: прогоняет каждого тем же
источником (дерево, индекс, коммит), забирает его находки «файл:строка: правило: описание» и сверяет с
поимённой базой из `RATCHET_BASELINE`. Стража под храповиком `run-all.sh` и pre-push напрямую не зовут: его
находки судит храповик.

- Находка без записи в базе — красный с адресом и готовым ключом (`ratchet-new`).
- Запись, чьего нарушения больше нет, — красный «запись устарела: исправленное убирается из базы тем же
  изменением» (`ratchet-stale`). Поэтому база только убывает.
- Запись убрана, а нарушение осталось, — оно снова новое, красный. Подмена (одно нарушение исправлено и
  убрано из базы, другое внесено) красная на новом, хотя число нарушений то же: база поимённая, а не счёт.
- Запись похожа на секрет или путь машины по правилам `guard-secrets.py` (`ratchet-secret`), строка не по
  форме, без причины или с повтором ключа (`ratchet-format`), запись для стража не из `RATCHET_GUARD`
  (`ratchet-unwired`) — красный.
- Оборачиваемый страж не найден, красный по предпосылке или с потерянной мишенью — красный, а не «ок».
- Зелёный прогон печатает долг: строку «принято …: долг: <причина>» на каждую запись и вердикт «ок: осмотрено N
  стражей под храповиком; долг: M».

**Формат записи.** По записи на строку: `<ключ>: <причина>`; пустая строка и решётка первым знаком —
комментарий. Ключ — `<страж>:<путь>:<правило>:<хэш>[#n]`, например
`check-text-hygiene.py:doc/notes.md:fffd:1a2b3c4d`. Хэш — первые 8 знаков SHA-256 нарушающей строки без
пробелов по краям; у находки без номера строки — её описания. Номера строки в ключе нет: вставка строк выше
нарушения ключ не меняет. Правка самой нарушающей строки ключ меняет: старая запись устаревает, новая
записывается тем же изменением. Одинаковые нарушающие строки одного файла различает суффикс `#2`, `#3` по
порядку. В записи нет значения секрета, токена или имени из списка: строка входит в ключ только хэшем, путь с
именем из списка страж имён уже показывает со звёздочками, причина пишется словами.

**Как добавить запись.** Красный прогон храповика печатает у новой находки «ключ для базы: …». Ключ
копируется в базу с причиной тем же изменением, которое принимает долг (обычно — включение стража на
проекте с накопленными нарушениями). База лежит в git, поэтому каждая новая запись видна в обзоре изменения;
молча она не появляется.

**Как убрать запись.** Нарушение исправляется, и его строка удаляется из базы тем же изменением: прогон
зелёный, долг на единицу меньше. Исправленное без удаления записи — красный «запись устарела».

**Новый проект начинает с пустой базы.** Комплект поставляет `ratchet.txt` только с комментариями и
`RATCHET_GUARD=off`: храповик печатает «судить нечего: храповик не подключён ни к одному стражу». Чтобы
подключить, назовите стража (`RATCHET_GUARD=check-text-hygiene.py`; несколько — повтором ключа) и прогоните
`python scripts/guards/check-ratchet.py`: при чистом дереве — «ок … долг: 0», при накопленных нарушениях —
красный с ключами, которые проект записывает в базу с причинами. Нет файла базы при включённом храповике —
«мишень потеряна». `RATCHET_GUARD=off` при непустой базе — красный: долг не исчезает молча.

В режиме `--commit` (pre-push) храповик видит только файлы коммита: записи файлов, которые коммит не меняет,
судят дерево в CI и индекс в pre-commit.

Храповиком не являются пометка `guard-allow` (исключение одной строки с причиной: постоянное, не убывает и не
считается) и проверка добавленных строк (`Source.added_lines`: судит только изменение и не помнит долга).

**Почему.** Ожидаемая ошибка без храповика: страж, включённый на проекте с накопленными нарушениями, красный с
первого дня, и его выключают целиком или обходят; без поимённой базы «долг не растёт» держится на счёте, а
счёт не видит подмену одного нарушения другим.

### Сообщение коммита

`guard-commit-message.py` (хук commit-msg, pre-push, CI по коммитам пуша): политика проекта — подпись
автора, запрещённые трейлеры, только ASCII, адрес автора — по ключам `COMMIT_*`; всегда — имя автора не
пусто, нет пути машины и имени из списка, сообщение не пусто. Сообщение судится в том виде, в каком git
его сохранит (`lib/message.py`: комментарии редактора и хвост за строкой-ножницами). `commit-range.sh`
решает, какие коммиты пуша судить: прошлые коммиты целевой ветки не судятся; первый пуш в пустой
удалённый репозиторий судит все коммиты ветки. **Почему:** сообщения
остаются в публичной истории навсегда.

### Хук агента

`scripts/agent-hooks/guard-git.py`, запись в настройках агента на инструменты Bash и PowerShell. Правила
(включаются ключом `AGENT_HOOK_RULES`): `add-all` (git add -A, -u, точка), `stash`, `force-push`,
`no-verify` (и `-n` у commit), `rewrite-history` (filter-branch, filter-repo), `config-user` (запись
user.name, user.email), `commit-scope` (commit без перечня файлов `--only`, `-i`, `--amend`, `--` и без
пометки `# index-verified: <причина>`), `flag-after-dashes`, `backtick` (обратный апостроф вне кавычек у
printf и python -c), `ps-write` (запись файла командами PowerShell с обратным апострофом), `commit-m-backtick`.
Это подсказка, а не барьер: псевдонимы, `bash -c` и запуск git из скрипта хук не видит. Нет параметров —
отказ команд с git с подсказкой; команды без git проходят. **Почему:** агент в общем рабочем каталоге одной
командой забирает чужие правки в коммит или прячет чужую работу; какие из этих правил нужны проекту,
решает проект.

### Страж с самотестом и вызывающим

`check-wiring.py`: у каждого стража есть шапка с метками «Зачем:», «Проверяет:», «Не проверяет:»,
«Правило:», самотест `selftest/test-<имя>.py` и внешний вызывающий (хук git или задание CI; стражей `check-*`
зовёт `run-all.sh`, которого зовёт задание CI); хуки из `HOOKS` исполняемые и зовут своих стражей; запись
хука агента покрывает Bash и PowerShell; файл параметров годен и лежит в git. `prove-red.sh` подменяет
каждого стража заглушкой «всегда успех» во временной копии и требует, чтобы его самотест упал на красной
пробе. Самотест обязан начинаться с законной пробы и содержать пробы всех четырёх видов: законное,
красная, иной-синтаксис, мишень. **Почему:** страж, которого никто не вызывает, или самотест, проходящий и
с заглушкой, выглядят надёжно и ничего не держат.

### Пустота не бывает чистой

`probe-empty-root.sh`: каждый страж дерева на пустом репозитории, папке без git и пустом каркасе печатает
«FAIL: мишень потеряна», «FAIL: предпосылка» или «судить нечего», но не «ок». **Почему:** страж, зелёный на
пустоте, после переименования папки или потери мишени стал бы вечно зелёным.

## Проба журнала CI

`ci-mask.sh` маскирует значения списка до любого шага, который мог бы их напечатать. Проверить, что
маскирование работает в настоящем журнале, можно только прогоном на сервере: заведите секрет
`<PRIVATE_NAMES_VAR>_PROBE` с выдуманными значениями, создайте ветку `probe/<имя>`, скопируйте
`scripts/guards/probe/probe-log.yml.tmpl` в папку заданий CI под именем `probe-log.yml`, запушьте ветку и
найдите значения в журнале: их быть не должно, а маркер `PROBE-MARKER` должен быть виден. Затем удалите
ветку.

## Привязки к окружению

Раскладка `.github/workflows/guards.yml` и `.claude/settings.json` принята владельцем методологии как
устройство комплекта (задача переноса стражей). Из неё следуют места, где синтаксис принадлежит
конкретным продуктам: синтаксис задания CI и команда маскирования журнала (`::add-mask::`), формат записи
хука агента и переменная папки проекта в его команде, префиксы токенов в `guard-secrets.py`. Проект с другим
CI или другим агентом переписывает эти файлы под себя и меняет ключи `CI_WORKFLOW`, `AGENT_SETTINGS`.

## Чего в комплекте нет

- Установщика настроек хостинга кода (защита ветки, заведение секрета): это настройка конкретного сервиса,
  а не проверка репозитория; секрет списка и защиту целевой ветки проект заводит сам.
- Проверок журнала хода, завязанных на формат проекта-источника: предела длины подписи у добавленных строк
  и формы записей журнала решений с даты перехода. Их можно выразить в будущем видом правила «добавленные в
  индексе строки» (`Source.added_lines` в библиотеке есть), но вид не введён, пока его не попросит проект.
