Статус: черновик

# Спецификация WC-2: общий контракт работы

**Статус:** контрактная спецификация; не реализация и не подтверждение совместимого runtime.

**Область:** контракт одного экземпляра `task` или `epic`, граф работ и версий артефактов, сериализованные события, состояния и переходы, политика изменения активной работы, вопросы владельцу и сопряжение с движком. Основание требований — [спецификация эпика](../../../work-coordinator-epic-spec.md) REQ-1–9 и AC-1–8, AC-10–12; состав проб — [план эпика](../../../work-coordinator-epic-plan.md), WC-2 и примеры общей приёмки. Маршруты — принятый WC-1 (06a8646); эта спецификация их не дублирует и не меняет.

## Контракт и границы

Один запуск принимает ровно один корневой объект типа `task` либо `epic`. Это один и тот же формат экземпляра с дискриминатором типа; задача не превращается в фиктивный одно-child epic. Epic содержит упорядоченные ссылки на дочерние экземпляры task/epic. Ссылка на ребёнка не передаёт его состояние родителю: каждый экземпляр имеет собственные идентификатор, ревизию, состояние и журнал событий.

Граф имеет два вида рёбер: `contains(parent, child)` и `depends(consumer, producer, accepted_artifact_pin)`. Объединённый граф обязан быть ацикличен до запуска; отвергающий переход сообщает воспроизводимый путь цикла и не меняет экземпляр. Идентификаторы рёбер и экземпляров стабильны. Включение и зависимости проверяются как при создании, так и при изменении графа.

Зависимость закрепляется за парой «этап, принятая версия артефакта» производителя, а не за его текущим состоянием или последним файлом. Версия неизменяема и адресуется идентификатором/ревизией артефакта; pin сохраняет ссылку на принятую версию и доказательство приёмки. Новая версия не передвигает pin автоматически. Изменение pin — отдельное событие пересверки с причиной и полномочным решением, если оно требуется политикой ворот.

Каждый экземпляр имеет монотонную ревизию и упорядоченный журнал принятых событий. Событие содержит уникальный id, целевой instance, ожидаемую ревизию, тип, основание/инициатора и необходимые ссылки на доказательства. Обработчик атомарно проверяет ожидаемую ревизию, полномочие и предусловия, затем применяет переход и увеличивает ревизию. Дубликат id возвращает сохранённый исход без второго эффекта; устаревшая ревизия отклоняется с текущей ревизией. События разных экземпляров могут исполняться параллельно; для одного экземпляра действует последовательная очередь/сериализатор. Порядок независимых экземпляров не задаёт порядок общего проекта.

Изменение постановки, входа, дочернего результата или графа после завершения не переписывает завершённый журнал или принятый артефакт: создаётся новый экземпляр/ревизия работы либо отдельное событие `reopen`, подтверждённое полномочным владельцем. Reopen создаёт новую рабочую ревизию, оставляя запись завершения и артефакты прежней ревизии читаемыми. Изменение активного входа допускается только по записанной политике этой работы. Если политика отсутствует или изменение не классифицировано, исполнитель переводит работу в `paused-change`; молчаливое продолжение и автоматическая отмена запрещены.

## Жизненный цикл и полномочия

Состояния экземпляра: `queued`, `ready`, `running`, `paused`, `paused-change`, `blocked-dependency`, `delivery-pending`, `waiting-owner`, `stopping`, `cancelled`, `compensation-pending`, `completed`, `failed`. Каждый экземпляр также сохраняет множество самостоятельных блокировок: явная пауза/stop, решение владельца, stale input/dependency, safety gate и неизвестный эффект. Событие удаляет только ту блокировку, на которую уполномочено; `resume` не снимает owner/safety/stale/effect-блокировки, а `reconcile` не снимает явную паузу или stop. Ответ владельца, пришедший во время явной паузы, сохраняется как pending input и не применяется до отдельного полномочного `resume`; он не снимает pause/stop latch. `start` допустим только из `ready` при пустом наборе блокировок, актуальных pins/входах, выполненных воротах и без активной паузы/HOLD. Иначе событие не меняет состояние и пишет причину отказа. `completed`, `cancelled` и `failed` терминальны для данной рабочей ревизии; дальнейшая работа требует новой ревизии или явного reopen.

Каждая блокировка имеет `blocker_id`, тип, причину, полномочного разрешающего и требуемое доказательство. Явную pause/stop снимает только полномочный `resume`; stale входы/pins — только успешная адресная `reconcile`; owner gate — только коррелированный ответ доверенного источника; safety gate — typed решение указанного владельца ворот; unknown effect — сверенный исход от владельца эффекта/источника истины. Никакая общая команда не очищает блокировки списком или по факту успешного шага.

| Состояние | Выход/переход | Ответственный |
|---|---|---|
| `queued` | `prepare` → `ready`, если обязательные зависимости pinned/приняты и нет блокировок; непринятая зависимость → `blocked-dependency`; прочий неразрешённый guard оставляет `queued` | координатор проверяет, host фиксирует |
| `ready` | `start` → `running` только после проверки всех блокировок/ворот; нарушение guard оставляет `ready` и отказывает; изменение входа → `paused-change` | host применяет только typed control; координатор проверяет guard |
| `running` | явный `pause` → `paused` с latch; смена входа → политика либо `paused-change`; сдача → `delivery-pending` | координатор и host; владелец задаёт политику |
| `paused` | `resume` снимает только явный pause/stop latch: при оставшихся блокировках остаётся `paused`, иначе → `ready` (не `running`); pending `owner_decision` применяется только после resume и только если прочие guards допускают исход; cancel → `cancelled`; вход изменён → остаётся `paused` со stale latch | полномочный инициатор/доверенный владелец, host |
| `paused-change` | `reconcile` пересчитывает только stale-блокировки; при активной pause/stop остаётся `paused`, при нерешённой политике остаётся `paused-change`; к `ready` допускает лишь после явного разрешения input-change и снятия всех блокировок | координатор пересверяет; владелец отвечает за отсутствующую политику |
| `blocked-dependency` | принята нужная версия и пройдена пересверка → `ready` только если нет иных блокировок; иначе остаётся blocked/paused с причиной | координатор проверяет pin, host фиксирует |
| `delivery-pending` | подтверждённая доставка по тому же intent id → `waiting-owner`; ошибка/unknown сохраняет intent и остаётся здесь | host восстанавливает/delivers; назначенный ответственный разбирает сбой |
| `waiting-owner` | stop → `stopping`, сохраняя owner-decision latch; доверенное `accept` → `completed` только при отсутствии других блокировок, иначе остаётся `paused` с зафиксированным решением и оставшимися блокировками; `return` → `ready` только без иных latch (иначе `paused`), `reject` → `failed`; дедлайн создаёт эскалацию, не меняя состояние | доверенный источник решения; host; назначенный ответственный |
| `stopping` | завершённый stop → `paused` с stop latch и сохранением всех прежних latch; отмена только отдельным полномочным `cancel` → `cancelled` | координатор исполняет stop; host сохраняет исход |
| `compensation-pending` | разрешено только для конкретного известного эффекта незавершённой ревизии; успех → `paused` с записью результата; отказ/unknown остаётся здесь, эффект не повторяется без безопасной сверки/ключа | исполнитель эффекта сообщает исход, host фиксирует; владелец эффекта решает unknown |
| `completed`, `cancelled`, `failed` | терминальны; только новая работа или отдельный полномочный `reopen` создаёт рабочую ревизию | координатор отвергает мутацию старой ревизии; владелец разрешает reopen |

| Событие | Допустимое состояние и условие | Итог | Исполнитель/ответственный |
|---|---|---|---|
| `prepare` | только queued; обязательные зависимости pinned и приняты, нет иных блокировок | ready; непринятая dependency → blocked-dependency; иной неразрешённый guard оставляет queued с причиной | координатор проверяет; host фиксирует |
| `start` | только ready; повторно проверены все самостоятельные ворота, holds, pins, входы и отсутствие pause/HOLD/stop | running; при нарушении guard — отказ без перехода; прямой start из queued отвергается | координатор проверяет; host фиксирует |
| `pause` / `resume` | running / paused; typed control и полномочие | pause ставит latch; resume снимает только pause/stop latch, применяет отложенное решение владельца только после снятия latch, переводит в ready лишь при отсутствии других блокировок; повторный `start` обязателен | host; инициатор указывается в событии |
| `input_changed` | любое активное состояние | по явной политике: продолжить после пересверки, pause либо отдельный stop; без политики paused-change. Решение по этому изменению не снимает уже существовавшие pause/stop/HOLD/owner/safety блокировки | координатор анализирует; владелец политики отвечает за решение |
| `reconcile` | paused-change либо stale downstream | пересверенные ветви обновляют только stale-блокировки; явный pause/stop/HOLD и owner/safety gates сохраняются; незатронутые ветви сохраняются | координатор; host фиксирует результаты |
| `stop` | активное | stopping, затем paused или остановка с зафиксированным исходом | полномочный инициатор; координатор исполняет |
| `cancel` | активное/приостановленное | cancelled; открытые будущие действия закрыты, совершённые эффекты остаются | полномочный инициатор; host фиксирует |
| `compensate` | только активная/приостановленная незавершённая ревизия и конкретный эффект с определённой компенсацией; terminal `completed`/`cancelled` не мутируется | compensation-pending и сохранённый исход; terminal effect требует отдельной compensation-work, связанной с исходной ревизией/effect id | полномочный инициатор; адаптер/исполнитель эффекта сообщает результат |
| `submit` | работа готова к сдаче | создаётся durable question intent, состояние `delivery-pending`; подтверждение доставки переводит в `waiting-owner` | исполнитель сдачи формирует; host сохраняет и доставляет |
| `owner_decision` | `waiting-owner` либо `paused` с сохранённым owner latch; коррелированный запрос доставлен | только typed `accept`, `return` либо `reject`; в `paused` событие durable, но pending до resume; применение accept/return учитывает все прочие блокировки, reject → failed с причиной | доверенный источник владельца; host проверяет доказательство |
| `resolve_blocker` | задан blocker id; инициатор полномочен именно для этого типа, приложено требуемое доказательство | снимается только названная блокировка; чужое/устаревшее/неполное разрешение отклоняется без смены состояния | host проверяет право/доказательство; владелец указанной блокировки решает |
| `task_failure` | ошибка исполнителя зафиксирована с причиной/кодом, retryability и ссылкой на доказательство | failed terminal данной ревизии; восстановление — новая работа/revision либо полномочный reopen, не очистка истории | исполнитель сообщает; host фиксирует; владелец решает reopen |
| `overdue` | только `waiting-owner` или `paused` с сохранённым owner latch; срок истёк, решения нет | та же блокировка + одна идемпотентная эскалация ответственному | host вычисляет; назначенный ответственный принимает эскалацию |

`stop` означает прекратить продвижение и сохранить состояние/возможность продолжения; `cancel` означает закрыть эту ревизию без обещания отменить уже совершённое; `compensate` — отдельное новое действие, обращающее конкретный эффект только при наличии определённой и допустимой компенсации. Ни одно из них не выполняет автоматический rollback. Неизвестный внешний исход остаётся `unknown`; повтор разрешён только с тем же безопасным ключом идемпотентности и установленной семантикой повтора. Без этого повтор блокируется, ответственный — владелец интеграции/эффекта. Компенсация эффекта, совершённого до `completed`/`cancelled`, оформляется новой компенсационной работой, которая ссылается на terminal instance/revision/effect id; она не меняет состояние, историю или артефакты terminal revision. Исход владельца `return` означает доработку в той же рабочей ревизии: текущий экземпляр остаётся нетерминальным, сохраняет журнал и guards и после исправления допускает повторную сдачу без создания работы или reopening. Исход `reject` терминально переводит текущую ревизию в `failed` с причиной; продолжить после него можно только новой работой/revision либо отдельным полномочным reopen, не переписывающим историю.

Входящие события изменения могут затронуть рекурсивно вложенные работы. Пересверка строит множество потомков по зависимостям и входным отпечаткам: устаревшими отмечаются только потребители, чьи закреплённые входы/права/ворота/дочерние результаты изменились. Выполняется топологически от производителя к потребителям; независимые ветви сохраняют pins и результат. Изменение завершённого узла создаёт новую работу/reopen, после чего та же адресная пересверка применяется к downstream. Никакое изменение не переписывает прежние события.

## Намерение вопроса и эффектов

Сдача атомарно сохраняет неизменяемое намерение вопроса: id/correlation id, instance и ревизию, адресата-владельца, вопрос, срок, ответственного за просрочку, ссылку на результат и ключ идемпотентности доставки. `waiting-owner` запрещён, пока host не восстановил это намерение и не зафиксировал связанное доказательство доставки с тем же id. Ошибка/неопределённость доставки оставляет состояние на воротах доставки; после рестарта host продолжает доставку того же намерения, а не создаёт новое.

Ответ владельца проверяется по доверенному источнику решений, области полномочий, предмету, корреляции и версии вопроса; текст агента о том, что «владелец сказал», доказательством не является. Повторная доставка того же ответа идемпотентна; противоречивый/устаревший ответ отклоняется и остаётся диагностическим событием. По истечении сохранённого срока host создаёт ровно одну эскалацию на ответственного с корреляцией к исходному вопросу. После рестарта срок пересчитывается по сохранённому времени и эскалация восстанавливается; просрочка не означает принятие, публикацию, отмену или снятие ворот.

Внешний эффект имеет durable запись до вызова: effect id, instance/revision, typed operation, ключ идемпотентности, ожидаемые последствия и статус `planned | in_progress | succeeded | failed | unknown | compensated`. Фиксация результата эффекта и перехода связываются журналом; память процесса не является учётом. После рестарта незавершённый `in_progress` сначала сверяется по ключу с адаптером/источником истины. При отсутствии подтверждённой безопасной сверки результат становится `unknown`, автоматический повтор запрещён. Exactly-once не обещается.

## Слои ответственности и сопряжение с движком

**Движок**: `task-runner.md` и [спецификация машины](../../../../state-machines/state-machine-spec.md) задают нормативную модель событийного шага и восстановления; сами по себе они не доказывают свойства исполняемой библиотеки. В опубликованном состоянии эпика 0.29 движок описан как типизированная машина со шагом и командами среды; тестовая среда использует in-memory handlers. Принятый кандидатом протокол событий задаёт контракт manifest/identity, event ingress, receipt, dedup, restore и запрета ложного exactly-once, но прямо не меняет runtime и не подтверждает conformance. Это раздельные источники: контрактный документ не равен runtime-функции.

Read-only сверка на опубликованном снимке эпика 0.29 `41a634d1ee464762067ba1547b9775fe27fa17e4`: спецификация описывает базовый runtime как 0.28; актуальное описание engine называет in-memory handlers тестовой средой, а настоящие handlers и host — отдельными результатами. Спецификация 0.29 прямо называет event protocol опытным кандидатом, не реализующим runtime. В том же snapshot план описывает отдельные runtime результаты lifecycle/recovery (D), host effects/outbox (E) и local conformance (F); evidence говорит, что их проверки будущие, а owner acceptance и выпуск ещё не состоялись. План оставляет backend открытым. Следовательно, **предоставлено как целевая спецификация**: typed event/receipt/dedup/identity и требования к durable inbox/outbox, apply/recovery и безопасным эффектам. **Не подтверждено как принятое runtime 0.29**: рабочая event admission/receipt граница, durable host effects/outbox и end-to-end conformance этих требований. Это подтверждённый разрыв между целевым контрактом и проверенной реализацией, но не диагноз дефекта конкретного кода. Точная зависимость для реализации: принять и проверить результаты D/E/F эпика 0.29 (или явно ограниченный совместимый контракт), затем WC-4 сверяет интерфейс host; пока этого нет, совместимый runtime обещать нельзя. Backend и место реализации не выбираются.

**Хозяин/координатор** владеет task/epic, графом, pins, пересверкой, владельческими воротами, дедлайном и дедупликацией намерений. Он выражает операции движка typed controls и проверяет предусловия до команды; произвольная строка или имя операции не исполняется. **Агентные оболочки** могут предложить содержимое/результат этапа, но не меняют состояние, не принимают решения за владельца и не удостоверяют полномочия. Сопряжение требует адаптера команд/событий движка и доверенного источника решения владельца; этим документом реализация адаптера не создаётся.

Долговечность журнала, inbox/outbox, pins и учёта эффектов — обязательное свойство будущего host, не заявление о конкретном хранилище, транзакции или backend. Хост обязан атомарно записывать событие/состояние/outbox-намерение до выдачи внешней команды и сохранять результат доставки/эффекта; при недоказуемой атомарности оставлять состояние неизвестным и не повторять небезопасно.

## Контрпробы

Каждая проба — требование WC-2 для последующих исполнимых сценариев WC-3, не тест уже существующего runtime. Приёмщик WC-2 проверяет наличие правила и определённого исхода; сценарии запускаются отдельно в WC-3.

| Вход / контрпример | Ожидаемый исход | Кто исполняет / проверяет |
|---|---|---|
| Обычная task; вместо неё подан искусственный epic с одним ребёнком | один task instance; wrapper отвергнут как лишняя сущность | координатор; проверяющий WC-3 |
| Epic содержит epic → task; затем потомок включается в предка, либо dependency образует цикл | вложенность принимается; цикл отклонён до запуска с путём, граф не изменён | валидатор графа; проверяющий WC-3 |
| Потребитель принял этап V1; производитель создал V2 | pin остаётся V1 после рестарта; только явная пересверка меняет его на V2 и инвалидирует затронутых потребителей | host/координатор; проверяющий WC-3 |
| Два события одного instance с одинаковой ожидаемой ревизией; одновременно два независимых instance | у одного instance выигрывает только допустимый первый переход, второй stale/replay не создаёт эффекта; независимые могут идти параллельно | сериализатор host; проверяющий WC-3 |
| В середине nested epic меняется вход одной ветви | без политики — paused-change; при принятой политике адресно инвалидируются downstream, незатронутая ветвь сохраняется | координатор; владелец политики; проверяющий WC-3 |
| `waiting-owner → stop → paused → resume` при нерешённом owner gate | resume снимает только stop latch, остаётся paused; start отвергнут до решения владельца. Ответ, доставленный до resume, остаётся pending и не меняет paused; после resume его исход всё ещё проходит остальные guards | host и доверенный владелец; проверяющий WC-3 |
| `paused → input_changed → reconcile → ready → start` при явном pause/HOLD | проба блокируется: reconcile не очищает pause/HOLD, `ready`/`start` недостижимы; после разрешённого снятия pause новая проверка start всё ещё требует пустых blockers | координатор и host; полномочный инициатор; проверяющий WC-3 |
| Изменён вход завершённой работы без нового instance/reopen | отклонить; исходный завершённый журнал и принятый артефакт неизменны | валидатор; проверяющий WC-3 |
| «Отменить» уже совершённый внешний эффект или компенсировать эффект без описанной компенсации | cancel не стирает эффект; compensation отклонена как неопределённая; эффект остаётся учтённым | host/владелец эффекта; проверяющий WC-3 |
| Отказ владельца `reject`; `task_failure`; компенсация эффекта terminal completed/cancelled | reject/failure дают failed terminal с причиной; reopen/new revision требуется для новой работы; terminal эффект обрабатывается только отдельной compensation-work, старый instance не мутируется | доверенный владелец, исполнитель, host; проверяющий WC-3 |
| `return → ready → start → submit` против `reject` | return повторно сдаёт ту же рабочую ревизию с исходным журналом и guards; reject оставляет её terminal failed, повторный start/submit в ней отклоняется | доверенный владелец и координатор; host фиксирует; проверяющий WC-3 |
| Сдача без созданного вопроса; переход в waiting-owner без доставленного коррелированного id | переход отвергнут; намерение/outbox восстанавливаются при рестарте без нового id | host; проверяющий WC-3 |
| Нет ответа к сроку, host перезапущен до/после срока | ответственному адресована одна восстановимая эскалация; принятия/публикации нет | host и назначенный ответственный; проверяющий WC-3 |
| Агент заявляет решение владельца; повтор эффекта со статусом unknown без безопасного ключа | forged decision отвергнуто; повтор эффекта заблокирован, состояние unknown сохранено | доверенный источник/host; проверяющий WC-3 |

## Трассировка требований

| Требование | Раздел/правило |
|---|---|
| REQ-1; AC-1 | Контракт и границы: единый task/epic, без wrapper |
| REQ-2; AC-2 | Контракт и границы: граф, циклы, принятые pins и stale |
| REQ-3; AC-3 | Контракт и границы: последовательность событий одного instance; параллельность независимых |
| REQ-4; AC-4 | WC-1 (06a8646); эта спецификация маршруты не перепроектирует |
| REQ-5; AC-5, AC-11 | Жизненный цикл: адресная пересверка, новая ревизия/reopen без переписи |
| REQ-6; AC-6, AC-12 | Жизненный цикл: политика активного входа; разные stop/cancel/compensate |
| REQ-7; AC-7 | Намерение вопроса и эффектов: intent, delivery proof, restart, deadline/escalation |
| REQ-8; AC-8 | Намерение вопроса и эффектов: trusted source, typed control, durable effect ledger, unknown |
| REQ-9 | Сопряжение с движком: границы и неподтверждённый контракт 0.29 |
| AC-10 | Таблица трассировки; полная проверка относится к WC-3/приёмке эпика, не объявляется исполненной WC-2 |

**Причина введения контракта:** ожидаемая ошибка — без общего формата и переходов задача может быть искусственно обёрнута, зависимости могут незаметно сменить входную версию, а неизвестный внешний эффект — исполнен повторно или замаскирован под rollback. Это проектируемые риски требований эпика, не заявление о наблюдавшемся сбое или о внедрённом поведении.
