# Сценарии приёмки WC-3: координатор работ

**Статус:** сценарии контрактной приёмки для будущего host; не реализация и не свидетельство выполнения runtime.

**Основание:** требования [эпика](../../../work-coordinator-epic-spec.md) и [плана](../../../work-coordinator-epic-plan.md); контракт [WC-2](../wc-2-common-contract/spec.md), включая разделы «Контракт и границы», «Жизненный цикл и полномочия», «Намерение вопроса и эффектов» и «Сопряжение с движком»; маршрутные правила [WC-1](../wc-1-rules/spec.md); дополнение 088 отражено в [карте основания](../../088-adresnye-blokirovki-voprosov-i-dokazanno/intent.md). База WC-2: `3e9034c96b51febb44b711be143e1a0aaaa8c204`. Эти сценарии не меняют контракт, маршрут или границы WC-2.

## Исполнение будущим host

Исполнитель каждого сценария подаёт указанные события и входные записи через контрактный интерфейс host, сохраняет исходные и конечные записи/журналы, ответы и диагностику. Проверяющий сопоставляет их с ожидаемыми исходами и предикатами; поиск текста или маркеров в исходниках не считается проверкой поведения. Для отказа обязательны и точная причина, и наблюдаемое отсутствие запрещённого перехода/эффекта. Идентификаторы ниже — условные уникальные данные одной пробы; часы и время просрочки задаются фикстурой. Пока host не создан, выполнение всех строк — будущее требование WC-4/5, runtime-прогоны не заявляются.

| ID | Вход и действия | Ожидаемый исход / наблюдаемое доказательство | Отрицательная проба: точная причина и исход | Ответственный / контракт |
|---|---|---|---|---|
| S01 | Подать корневую `task`; отдельно подать `epic → epic → task`. | Первая запись — ровно один task instance; вторая сохраняет все уровни и типы, каждый со своим id, ревизией и журналом. | Подать task как искусственный epic с одним task-ребёнком: вход отвергается как лишняя обёртка; второго фиктивного instance нет. | Host/координатор; WC-2 §«Контракт и границы». |
| S02 | Создать корректную nested структуру, затем добавить `contains` от потомка к предку; отдельной пробой замкнуть `depends`-цикл. | Оба изменения графа отклонены до запуска; диагностика содержит воспроизводимый замкнутый путь, исходные вершины/рёбра и ревизии не меняются. | Если цикл принят либо старт состоялся, проба падает: нарушена ацикличность объединённого графа. | Валидатор графа; WC-2 §«Контракт и границы». |
| S03 | Потребитель принимает pin на артефакт этапа V1; производитель выпускает V2; перезапустить host; затем выполнить полномочную reconcile. | До reconcile pin и доказательство приёмки остаются V1 после рестарта. Только reconcile с причиной/полномочием может сменить pin; только реально затронутые потребители stale. | Прямое автоматическое смещение pin на «последнюю» V2 отвергается как отсутствие отдельного события пересверки; pin остаётся V1, потребитель не меняет вход. | Host/координатор; WC-2 §§«Контракт и границы», «Контрпробы». |
| S04 | Два события одного instance имеют одинаковую expected revision и допустимы по отдельности; параллельно продвигать другой instance. | Для первого instance принят только один последовательный переход; второе событие получает сохранённый replay/stale исход без второго эффекта. Независимый instance продвигается параллельно. | Повтор id не создаёт второго эффекта; stale revision отвергается с текущей ревизией, состояние первого не меняется повторно. | Сериализатор host; WC-2 §«Контракт и границы». |
| S05 | В nested epic изменить вход среднего уровня во время работы; выполнить адресную reconcile. | Пересчитаны только зависимые входы, pins, права, ворота, результаты и дети; незатронутая параллельная ветвь сохраняет pin, результат и журнал без перезапуска. | Попытка объявить всё дерево актуальным без пересчёта зависимых данных отклоняется как неполная reconcile; stale latch затронутых узлов остаётся. | Координатор; WC-2 §«Жизненный цикл и полномочия». |
| S06 | Изменить вход/результат завершённой работы, затем отдельными ветками создать новую работу и выполнить полномочный reopen. | Разрешён только новый instance/revision либо явно подтверждённый reopen; прежние завершённые события и принятый артефакт остаются неизменными и доступны. | Мутация terminal revision без нового instance/reopen отклонена как попытка изменить завершённую историю; ни журнал, ни артефакт не изменены. | Координатор/владелец; WC-2 §§«Жизненный цикл и полномочия», «События». |
| S07 | На активной работе изменить вход при отсутствии политики; затем попробовать продолжить и отменить её молча. | Работа получает `paused-change`; исходный вход и работа сохранены, дальнейшее продвижение ждёт явной политики/решения. | `continue` и `cancel` без применимой политики отвергнуты именно из-за отсутствия политики изменения активного input; остаётся `paused-change`, скрытого эффекта/отмены нет. | Координатор, владелец политики; WC-2 §«Жизненный цикл и полномочия». |
| S08 | Для отдельного instance последовательно поставить pause/stop, HOLD, owner, safety, stale и unknown-effect blockers; выполнить `reconcile`, `resume`, затем `start`. Проверить каждый тип отдельным blocker id. | Снимаются только адресные blockers уполномоченными доказательствами. Reconcile очищает только пересверенные stale blockers; resume — только pause/stop latch; HOLD, owner, safety и unknown effect сохраняются. Start возможен лишь после отдельного снятия всех блокировок. | Общая reconcile/resume, неверный blocker id, полномочие или доказательство отвергаются с причиной «не тот blocker/неполномочное действие/недостающее доказательство»; blocker set и состояние не дают перейти в running. | Host, координатор и владельцы соответствующих ворот; WC-2 §§«Жизненный цикл и полномочия», «События». |
| S09 | Доставить корректное owner decision, пока активна явная pause/stop; проверить запись, затем выполнить разрешённый resume. | Решение сохраняется как pending input и не меняет приостановленное состояние; resume снимает только явный latch, применяет pending decision лишь после этого и только при успешных остальных guards. | Попытка применить решение до resume отвергается как активная явная пауза; pause/stop latch не снят, перехода/эффекта нет. | Host и доверенный источник владельца; WC-2 §§«Жизненный цикл и полномочия», «События». |
| S10 | Для чистого queued instance выполнить `prepare`, затем `start`; отдельный instance запустить непосредственно из queued. | Нормальная цепочка ровно `queued → ready → running` через prepare и start; каждое событие и ревизия записаны. | Прямой start из queued отвергается, потому что start допустим только из ready после проверки guards; состояние queued, ревизия и внешние эффекты не меняются. | Координатор/host; WC-2 §§«Жизненный цикл и полномочия», «События». |
| S11 | На `waiting-owner` получить коррелированный `return`, исправить результат и повторно сдать его; проверить ту же revision и историю. | Return оставляет revision нетерминальной; после исправления допустимы повторная сдача и новый вопрос intent согласно контракту, исходный журнал сохраняется. | Повторная сдача до разрешения необходимых blockers/исправления отвергается по соответствующему guard; revision не становится новой автоматически. | Владелец/host; WC-2 §«Жизненный цикл и полномочия». |
| S12 | В отдельных прогонах получить доверенный `reject`, зафиксировать `task_failure` с причиной, retryability и доказательством. | Reject и task_failure переводят данную revision в terminal `failed`; причина и событие остаются в журнале. Продолжение требует новой работы/revision или полномочного reopen. | Повторный start/submit в failed revision отвергается как terminal; состояние и история не очищены. | Доверенный владелец, исполнитель и host; WC-2 §«События». |
| S13 | Известный terminal effect completed/cancelled попытаться компенсировать в исходном instance; затем создать отдельную compensation-work со ссылкой на revision/effect id. | Первое действие не меняет terminal instance; отдельная работа допускает только конкретную разрешённую компенсацию с собственным журналом и сохранённой ссылкой. | Мутация terminal instance либо компенсация без определённой операции отвергается как terminal effect/нет определённой компенсации; исходный эффект и терминальная история неизменны. | Владелец эффекта/host; WC-2 §«События». |
| S14 | Выполнить submit результата; проверить durable question intent до доставки, затем подтвердить доставку с тем же correlation id. | До внешней доставки сохранены intent id, instance/revision, адресат, вопрос, срок, ответственный, result ref и idempotency key. Только receipt доставки того же intent разрешает `waiting-owner`. | Просьба перейти в waiting-owner без intent или коррелированного delivery proof отвергается из-за отсутствия доказательства доставки; остаётся delivery-pending, новых решений нет. | Host/ответственный доставки; WC-2 §«Намерение вопроса и эффектов». |
| S15 | Оставить intent недоставленным, перезапустить host и повторить восстановление; затем доставить/повторить тот же receipt. | Восстанавливается тот же intent и id; успешная доставка фиксируется один раз, повтор receipt возвращает прежний исход, не дублируя вопрос или решение. | Создание второго id при рестарте отвергается как нарушение идемпотентности; исходный intent остаётся единственным и восстанавливаемым. | Host; WC-2 §«Намерение вопроса и эффектов». |
| S16 | Не дать ответа до сохранённого срока; проверить до срока, после срока и после рестарта после просрочки. | До срока эскалации нет. После срока ровно одна коррелированная эскалация направлена назначенному ответственному; рестарт восстанавливает её идемпотентно, owner gate остаётся открытым. | Нет эскалации после срока — проба падает; попытка породить вторую при повторе отвергается как дубликат. Ни принятия, ни публикации не происходит. | Host вычисляет; назначенный ответственный принимает; WC-2 §«Намерение вопроса и эффектов». |
| S17 | Подать owner decision с корректным содержимым, но только с самоописанием агента как доказательством авторства; затем подать доказательство доверенного источника. | Поддельное решение не применяется; корректно удостоверенное решение проверяется по источнику, полномочию, корреляции и версии вопроса. | Forged decision отвергнуто за отсутствие доверенного proof; состояние, owner gate и артефакт не меняются. | Host/доверенный источник; WC-2 §«Намерение вопроса и эффектов». |
| S18 | Записать effect intent до вызова; после рестарта получить `unknown` без безопасной сверки/ключа; повторить попытку. | Сохраняется unknown и исходная durable запись; без доказанного безопасного ключа автоматический retry запрещён. Разрешённая сверка с источником истины может установить исход отдельной записью. | Blind retry отвергнут из-за unknown outcome и отсутствия безопасной сверки/семантики повтора; второй внешний вызов не сделан. | Host/владелец эффекта; WC-2 §«Намерение вопроса и эффектов». |
| S19 | Таблично подать full, разрешённый fast, запрещённый автоматический fast, fast по подтверждённому слову владельца, неполный fast, разрешённые пропуски и значения времени включая отсутствующие/превышающие ориентиры. | Упорядоченный маршрут, только явно разрешённые пропуски, полномочия и причины отказа соответствуют WC-1; safety-ворота сохраняются. Метрики времени записываются честно и не меняют допуск. | Неполный fast/неполномочное слово/запрещённый пропуск отвергаются с конкретной недостающей предпосылкой и без старта пропущенного этапа. Один лишь срок/T не является причиной отказа или остановки. | Координатор/владелец по полномочиям WC-1; [WC-1 сценарии](../wc-1-rules/spec.md). |
| S20 | Сквозной nested epic: две независимые задачи параллельно; изменить вход только одной во время выполнения; сохранить версии, перезапустить host, восстановить intent/delivery и доверенное owner decision, выполнить сборку и общую приёмку. | Обе ветви стартуют независимо; после изменения stale и повторное выполнение адресованы только затронутой ветви; вторая сохраняет результат. После рестарта pins, журнал, intent и доставка восстановлены; общая приёмка объединяет принятые результаты. Приёмка и публикация — самостоятельные полномочные исходы, никакой auto-acceptance/publication. | Потеря pin/intent, дублирование delivery/escalation, перезапуск незатронутой ветви, пропуск общего gate или автоматическая публикация проваливают сценарий с указанием конкретного несоответствия и сохранённых записей. | Host/координатор/ответственный общей приёмки; WC-2, AC-9. |

## Границы результата

Сценарии задают проверяемые входы, действия, положительные и отрицательные исходы, ответственных и наблюдаемые записи для будущего host. Они не выбирают backend, место реализации, адаптер или способ хранения, не реализуют стенд и не утверждают conformance эпика 0.29. Фактический запуск сценариев — следующий этап; до него результат имеет статус спецификации сценариев.
