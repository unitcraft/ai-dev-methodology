# Алула: причины, цели и история создания

Алула (`Alula`) — язык записи стейт-машин таблицами с формальными столбцами; описание — [state-machine-alula-spec.md](../state-machines/state-machine-alula-spec.md). С 2026-10-19 по 2026-10-21 (версии 2.7–2.13) язык назывался «Портолан» (`Portolan`); в разделах 1–9 он назван так, как назывался тогда, и имена файлов там тогдашние (`*.portolan.md`, `*.portolan.json`, `state-machine-portolan-spec.md`, `check-portolan-*.py`); с версии 2.14 (2026-10-21, метка AL-50) — `*.alula.md`, `*.alula.json`, `state-machine-alula-spec.md`, `check-alula-*.py`. Почему имя сменили — раздел 10. Этот файл — не норма, а запись о том, зачем язык появился, что от него требовалось и как он дошёл до нынешнего вида. Путь до Портолана начался с алгоритма прозой 2026-10-06…07 (раздел 2); сам формат вырос за один день, 2026-10-19, из уже существовавших таблиц состояний и кода автоматов; даты без года-месяца — 2026-10-19. Слова владельца записаны с датой и источником (правило методики о слове владельца, `task-sessions.md`, «Правила»). Пути к прежним файлам машин в этой хронике даны по нынешнему положению (в `state-machines/archive/`).

## 1. Что это и чего хотели

**Портолан** записывает машину — процесс с состояниями, событиями, условиями, действиями и вложенными вызовами других машин — таблицами в markdown. Файл машины читает и пишет человек по-русски; из него программа получает проверки, JSON-дерево и исполнение.

**Цели**

1. **Описывать машины без программирования на Нове.** Владелец, 2026-10-19: «как можно строить стейт машины внутри продукта … на человеческом языке миную стадию перепрограммирования на Нова, есть идеи?»
2. **С теми же возможностями, что у машин на Нове:** детерминированный повтор шага (правила 12–13 спецификации), вложенные вызовы (правило 35), структурный журнал (правило 31), счётчики, таблицы маршрутов, списки структур.
3. **С соблюдением правил методики.** Язык не вводит новых норм поведения: всё, что в нём записано, выводится из правил `state-machine-spec.md` (шаг как фиксация, шаг читает только свой Вход, один запрос — один ответ).
4. **Одна запись — один источник правды.** Код на Нове по таблицам не генерируется: третьего источника нет.
5. **Читаемость и проверяемость вместе.** Человек видит таблицы; программа проверяет достижимость состояний, полноту развилок, чтения и записи данных, соответствие журнала шаблонам.
6. **Проверка равенства с рукописным кодом по журналу.** Интерпретатор и автомат на Нове на одной последовательности событий дают одну последовательность (состояние, событие журнала, данные машины).

## 3. Причины появления

Проект-потребитель методики строит продукт, в котором пользователь должен описывать собственные машины, не программируя на Нове. Ему нужен был общий интерпретатор, читающий описание машины как данные. Первый ответ методики (владелец принял его «по рекомендации») был осторожным: источник правды оставить в коде автоматов на Нове, потому что в таблицах нет условий и действий, а универсальный язык по описанию — это второй язык программирования. Решающим стало слово владельца: «Мы не знаем заранее, достаточно ли такого языка для ваших реальных машин — реальные машины есть в этой методике» (владелец, 2026-10-19). Это превратило вопрос из «нужно ли» в «проверим выразимость на настоящих машинах».

**Почему не готовый язык.** Рассмотрены SCXML, XState, Amazon States Language, CNCF Serverless Workflow, BPMN/DMN, Temporal, а для условий — CEL, FEEL, JSONata. Целиком ни один не подошёл: у наших машин особая семантика (сохраняемая очередь событий, шаг как атомарная фиксация, «один запрос — один ответ», необратимое после фиксации, пауза цепочки вложенных машин), а исполнитель должен быть на Нове. Взята семантика CEL как образец (не Тьюринг-полный, детерминированный, без побочных эффектов), структура — в духе XState и Serverless Workflow.

## 4. Ключевые решения и их причины

| Решение | Причина |
|---|---|
| Таблицы с формальными столбцами вместо отдельного языка | строка таблицы уже единица проверки (метки `ИМЯ #n`); человек и программа читают один файл |
| Файл машины — единственный источник; код не генерируется | без третьего источника правды нет расхождений между прозой, таблицами и кодом |
| Закрытый чистый язык выражений без циклов (фильтр, отобразить, свёртка, диапазон), условия `если … то … иначе` | детерминизм (правила 12–13); простота интерпретатора; тотальность вычислений |
| Эффекты — только именованные примитивы с классами `pure`/`reading`/`writing`/`irreversible` | видно, что чисто, что читает, что пишет; необратимое только после фиксации шага |
| Структурный журнал: событие (код, параметры), шаблоны текста — отдельно | машина не собирает текст; журнал читается программой и показывается по-русски |
| Правило «функция без тела в источнике — примитив хозяина» | не изобретать тела, которых нет в источнике |
| Нотация как в Нове: объявления `имя тип` через пробел, `->` для результата, `...` для спреда, поля кортежа с нуля | одна нотация в таблице машины и в Нове (владелец, 2026-10-19, через проект-потребитель: «в Нова нет двоеточия перед типом, почему тут решил добавить?»); расширения помечены в разделе 14 формата |
| Закрытый набор значений `"a" \| "b"` вместо `текст из {…}` | единообразие с вариантами и перечислениями; правило, когда набор, а когда перечисление |
| Строки-ключи состояния — элементы списка | предпросмотр markdown склеивал соседние строки в один абзац (замечание владельца, 2026-10-19, по снимку экрана) |
| Проза в файле — комментарий; раскрытие фрагмента — отдельный справочный раздел | замечания переводчика проекта-потребителя при разборе образца |
| `ид` — тип UUID; `новый_ид` — reading-примитив, значение фиксируется в событии `сразу` | недетерминированность снимается как у времени; конверт запроса и трассы не меняются |

18. **Формат 2.13 — выпуск упрощений** (2026-10-20, метки AL-38…AL-49). Перечень упрощений составлен по замечаниям проекта-потребителя (его среда исполнения, задача о вложенных машинах и проверке цикла); слово владельца, 2026-10-20: согласовано. Что каждое упрощение убирает и почему:
    - **слово ворот — сигнал стороны** (AL-38): убраны событие `слово(…)`, тип и столбец «слова ворот»; слово человека, усиленного и вратаря объявляется сигналом в столбце «сигналы» своей стороны и, как прежде слово, относится к её открытому запросу по правилам 15–19. *Почему:* два вида событий ворот (`слово`, `сигнал`) различались только тем, кто может их подать, а это говорит объявление у стороны. Что среда исполнения потребителя доставляет слово человека входным событием без идентификатора запроса, — открытый пункт раздела 14 спецификации: согласовать с правилами 15–19;
    - **`Запрос:` и `Читает:` вместо одного `Вход:`** (AL-39): одно слово означало два разных ключа JSON (`inputs` у обращения, `reads` у остальных) и совпадало с разделом `## Вход` машины;
    - **пустые значения не пишутся** (AL-40): ключ с пустым значением (`—`, `нет`) пропускается — убраны `Вход: нет`, `Срок тишины: —`, `При входе: —`, строки, которые ничего не сообщали; ключ с настоящим значением по умолчанию (`Срок тишины: 0`, `Возвратов формы: 0`) может остаться написанным;
    - **«значения» вместо «слов значений»** (AL-41, ключ JSON `values`): слово «слово» означало в языке три разные вещи (ключевое слово, слово ворот, текст элемента перечисления); теперь — только ключевые слова;
    - **знаки только ASCII** (AL-42) и **одна запись типа** (AL-43): убраны пары `≥`/`>=`, `→`/`->`, `∈`/`in` и др. и синоним `HashMap[K, V]` — два написания одного удваивали таблицу слов, правила канонического вида и разбор без пользы для смысла;
    - **нет раздела «Раскрытие фрагмента»** (AL-44): его не читали ни разбор, ни проверки, а его таблицы расходились с фрагментом вручную; круг «md → JSON → md» проверяется равенством деревьев;
    - **канонический вид — рекомендуемый** (AL-45): генератору нормативно только равенство дерева после обратного перевода; правила 1б — рекомендация, а не второе требование;
    - **JSON-имя — одно правило, одно место** (AL-46): прежде латинское имя задавали скобки заголовка состояния, поиск по словарю (элементы перечислений, примитивы, привязки фрагмента) и молчаливое «имена по словарю» английского образца; теперь JSON-имя пишется в скобках при объявлении имени (в том числе у имени настройки вратаря в `human или agent по настройке <имя>`), словарь только предлагает имена;
    - **уточнения потребителя** (AL-47…AL-49): совместимость `число` и `число>=n` при сверке входа вложенной машины, отсутствующее необязательное поле входа — `пусто`, привязка `причина` — читаемое имя, JSON-имя `reason` (слово владельца, 2026-10-20: «reason лучше, чем prichina»).

    Раздел «Резерв» (`Правит`, `Возвратов формы`, `разбор`, `передать`, профиль стороны) не заведён: каждая из этих конструкций используется образцами («Совещание», «Шаг агента»), поэтому они остаются в ядре 2.x. Образцы «Шага агента» (русский и английский) и запись «Совещания» переписаны на 2.13; хеши образца файла определений пересчитаны; `check-portolan-keywords.py` проверяет и запись «Совещания», знаки операторов и JSON-имена.

19. **Алула 2.15 — выпуск упрощений** (2026-10-22, метки AL-51…AL-55; язык уже называется «Алула», имена файлов — нынешние). Слово владельца методики, 2026-10-21 (чат методики): «сразу вносите изменения в Алулу сейчас»; остальное — «по рекомендации и как договорились». Что и почему:
    - **свободный ввод вместо «стены»** (AL-51) и **необязательный `счётчик`** (AL-52): обращение к человеку без ворот (чат в покое: слово без идентификатора ворот ведёт переход) правила спецификации знали с задачи 064, а Алула записать его не могла — столбец `счётчик` был обязателен у каждой стороны. ## 9. Схемы `machine/2` и `scenario/0`: что это и для чего

Эти два вида JSON-файлов ведёт проект-потребитель Портолана (интерпретатор, переводчик, прогонщик сценариев на Нове); описания схем лежат у него в виде JSON Schema. Раздел записан по тому, что в них сказано на 2026-10-19; нормативного статуса в методике он не имеет.

**Цепочка.** `agent_step.portolan.md` (пишет человек, по-русски или по-английски) → переводчик → `agent_step.portolan.json` (схема `machine/2`) → интерпретатор исполняет машину; `*.scenario.test.json` (схема `scenario/0`) проверяют, что машина ведёт себя как ожидается. Имя дерева — `<имя>.portolan.json` (решение владельца, 2026-10-19, версия языка 2.10): JSON — исполняемая форма самого языка, а не отдельный формат, рукописное дерево — тоже Портолан в JSON-виде; `format: "machine/2"` внутри не меняется; переходного периода для прежних имён нет (версия 2.11). Раньше результат называли `*.machine.json` (суффикс по виду данных, `*.portolan.json` был отклонён по независимым мнениям); владелец решил иначе. Сценарии называются `<имя>.scenario.test.json`. Обратное преобразование дерева в файл Портолана — канонический вид, раздел 1б спецификации.

### 9.1. `machine/2` — машина как данные

Дерево, которое исполняет интерпретатор продукта. Поле `format: "machine/2"` обязательно; неизвестный ключ — отказ загрузки. Одно и то же дерево получается из русского и английского файла на Портолане (ключи английские). Схема проверяет форму; правила между разделами (чтения против `Вход`, записи против данных, достижимость, классы примитивов, полнота «Концов») проверяет программа проверки таблицы, схемой они не записываются.

Верхний уровень: `format`, `table_format` (необязательно: версия формата исходника; у рукописного JSON его нет), `machine` (латинское имя), `version`, `title`, `types`, `constants`, `params`, `input` (поля и инварианты входа), `data`, `parties`, `request_limit`, `signals`, `definitions`, `includes`, `initial` (начальное состояние), `error_end`, `common_events`, `states`, `ends`, `primitives`. Обязательны `format`, `machine`, `initial`, `states`, `ends`.

Соответствие строки Портолана и узла дерева (развилка `Check` небольшой машины-счётчика):

```text
### Check — fork
- Reads: count

| № | Condition | Actions | To |
|---|---|---|---|
| 1 | count >= LIMIT | journal(reached_limit, count: text(count)); stop = "done" | Finish |
| 2 | else | — | Step |
```

```json
{
  "name": "Check", "kind": "fork", "reads": [ "count" ],
  "rows": [
    {
      "n": 1, "event": { "kind": "now" },
      "cond": { "op": ">=", "left": { "op": "name", "name": "count" }, "right": { "op": "name", "name": "LIMIT" } },
      "actions": [
        { "do": "journal", "code": "reached_limit", "params": [ { "name": "count", "value": { "op": "call", "fn": "text", "args": [ { "op": "name", "name": "count" } ] } } ] },
        { "do": "assign", "target": "stop", "value": { "op": "lit", "value": "done" } }
      ],
      "to": "Finish"
    },
    { "n": 2, "event": { "kind": "now" }, "else": true, "to": "Step" }
  ]
}
```

Что видно: строка таблицы — элемент `rows` с номером `n`; условие — дерево выражения (`op`, `left`, `right`, `name`, `lit`, `call`); действия — список объектов с `do` (`assign`, `journal`, `add`, `bind`, `journal_all`); «Куда» — `to`; `иначе` — `else: true`; вид состояния — `kind` (`appeal`, `operation`, `fork`, `end`); `reads` — имена из строки «Reads» («Читает», до версии 2.13 — «Вход») состояния; «Концы» лежат отдельно в `ends` (строки `state`, `n`, `when`, `answer`).

### 9.2. `scenario/0` — тест поведения машины

Сценарий записывает: машине приходят события; после каждого шага ожидаются состояние, строки структурного журнала, подмножество данных, очередь, открытые запросы, отправленные и отменённые запросы, итог. Часть, которая не названа, не сравнивается. Прогонщик подаёт события интерпретатору и сверяет результат с ожидаемым.

Поля сценария: `format: "scenario/0"`, `machine` (латинское имя машины), `name`, `start_at` (часы мира в миллисекундах, по умолчанию 1000), `params` (значения параметров машины, которые задаёт проект), `steps`. Шаг: `do` (`feed` — подать событие), `event` (`kind`: `start`, `answer` и др.; `request`; `input` или данные ответа), `host` (ответы примитивов хозяина на этом шаге), `expect` (`state`, `journal`, `data`, `open`, `sent`, `outcome`). Значения составных типов записаны без потерь (`$record`, `$variant`).

Сокращённый шаг (реальный сценарий «Шага агента»: ход закончен, ответ проходит проверку и учёт, машина доходит до конца):

```json
{
  "format": "scenario/0",
  "machine": "agent_step",
  "name": "AGENT TURN 1: a finished turn goes through the check of the reply to the accounting and the end",
  "start_at": 1000,
  "steps": [
    { "do": "feed", "event": { "kind": "start", "request": "call-1", "input": { "agent_request": { "…": "…" } } },
      "host": { "reply_validation": { "$variant": "ReplyCheck", "name": "Valid", "fields": {} }, "close_agent_turn": null },
      "expect": { "state": "AgentTurn", "journal": [], "data": { "turn_count": 1, "turn": "first" }, "open": ["agent-1"], "sent": ["agent-1"] } },
    { "do": "feed", "event": { "kind": "answer", "name": "agent_done", "request": "agent-1", "input": { "$variant": "TurnResult", "name": "Finished", "fields": { "…": "…" } } },
      "expect": { "state": "End", "journal": [ { "code": "agent_usage", "params": { "…": "…" } } ], "open": [] } }
  ]
}
```

«…» — места, где реальный файл длиннее; показан порядок и ключи. Для «Шага агента» в проекте-потребителе 75 таких сценариев, для небольшой машины чата — 39; сравнение с кодом автомата идёт по структурному журналу (код события и параметры), поэтому сценарий проверяет именно журнал, а не текст.

## 10. Как выбирали имя (второй раз): Портолан → Алула

Имя «Портолан» продержалось с 2026-10-19 по 2026-10-21 (версии 2.7–2.13). Поиск нового имени шёл 2026-10-19…21 в несколько кругов; решение — слово владельца, 2026-10-21: «Alula - ОК».
